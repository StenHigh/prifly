## Context

См. proposal.md — Why. Требование присутствия раннеров живёт в
`checkExistingProjectRunners` (`cmd/prifly/project.go:2316`), которую зовёт
`existingProjectProfile`, а её — `projectInit` и путь `runners add`. Проверка
не различает host, который просят подключить, и остальных объявленных.
`project runners update` уже умеет иначе: он обновляет присутствующие и
перечисляет отсутствующие в `missing_hosts`, не отказывая.

Путь рабочей копии приходит из `WorktreeClaim.Path`, записанного относительно
authority root; `project start` отдаёт его как есть рядом с
`repository.toplevel`, поэтому читается он как относительный репозиторию.

`--prepare` печатает `execution[].environment` целиком; README (строка 129)
обещает, что environment в итог не печатается. Одно из двух неверно.

## Goals / Non-Goals

**Goals:**
- Клон подключается к существующему профилю одной документированной командой.
- Отказ, который всё же случился, называет исполнимый выход.
- Хост не ищет рабочую копию перебором.
- Вывод и README говорят о секретах одно и то же.

**Non-Goals:**
- Автосоздание раннеров чужих хостов при `init` (это выбор владельца, а не
  побочный эффект подключения машины).
- Форма передачи секрета без литерала (`env_from`) — отдельное изменение.
- Чистка папок попыток и `task.json` — сначала измерение, потом решение.

## Decisions

1. **`init` требует раннер только названного `--host`**, остальные
   отсутствующие называет в ответе полем `missing_hosts`, как `runners
   update`. Альтернатива «init создаёт недостающие раннеры сам» отвергнута:
   она молча добавляет в чужой clone файлы для хостов, которых там не держат.
2. **`runners add --host NAME` перестаёт звать общую проверку** и смотрит
   только на named host: отказ `project_runner_conflict` остаётся, отказ
   «отсутствует чужой» уходит. Это снимает замкнутый круг целиком.
3. **Отказ называет выход.** Там, где раннер назван и присутствует, но
   изменён, `safe_next_actions` получает `project.runners.update` и
   `project.runners.add`; пустая справка остаётся только там, где выхода
   действительно нет.
4. **Путь рабочей копии — абсолютный** в ответе `project start` и в задаче.
   Альтернатива «пометить, относительно чего» сохраняет лишнее звено: хост
   всё равно должен знать authority root, а он у него есть только из
   `local.yaml`. Абсолютный путь читается одинаково всеми.
5. **Итог перестаёт печатать значения environment, оставляя имена.**
   Обратный выбор (поправить README) отвергнут: значение переменной — то
   самое место, куда проект кладёт секрет, а итог уходит в терминал и журнал
   хоста. Имена достаточно, чтобы владелец проверил состав.

6. **`session task --all` вручает каждую перечисленную попытку** и пишет
   `task.json`, как форма с одной. Различие «чтение против вручения» заведено
   ради машинного монитора, который перечисляет выданные задания всех
   authority на машине и обязан оставаться наблюдателем; но монитор ходит
   через API, а не через CLI, и в CLI обе формы — это хост, спрашивающий свою
   работу. Альтернатива (поправить справку и оставить `--all` чтением)
   дешевле на один тест, но оставляет обещанный файл недостижимым для всех,
   кто следует нашему же раннеру.

## Risks / Trade-offs

- [Читатель, полагавшийся на значения environment в `--prepare`] → имена
  остаются, значения читаются `project local set` на своей машине.
- [Абсолютный путь в ответе делает вывод менее переносимым между машинами] →
  он и не переносим: claim принадлежит одной authority на одной машине.
- [Clone без раннера названного хоста] → отказ остаётся и называет файл,
  который нужно добавить, и команду, которая это делает.
- [`--all` начинает писать в рабочие папки] → пишет только то, что и так
  вручено этим же вызовом; монитор остаётся на API и ничего не пишет.
