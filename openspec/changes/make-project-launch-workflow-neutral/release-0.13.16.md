# Выпуск Pri-Fly 0.13.16

Решение владельца: слишком дорого искать прогоны по всему диску и слишком трудно
потом найти их, чтобы почистить. Одно место, одна популяция, старое — удалить.

## Число, с которого всё началось

Монитор, автоматически поднятый чужим `run start`, за одно сканирование обошёл
**953 692 каталога** — раз в минуту. Он искал авторитеты по дому, `/tmp` и `/`,
потому что не знал, где ещё они могут быть.

## Одно место: `~/.prifly/`

Всё, что Pri-Fly держит для пользователя, теперь под одним каталогом:

```
~/.prifly/monitor/sources/   реестр — по файлу на авторитет, только путь
~/.prifly/authorities/       авторитеты проектов, созданных без явного --state-root
```

Раньше это лежало в платформенном config-каталоге (`~/Library/Application
Support/Pri-Fly/` на macOS), а авторитеты — где их поставил тест или команда.
Удалить все локальные запуски, созданные по умолчанию, — значит удалить
`~/.prifly`. Авторитет, созданный по явному пути (`init DIR`, `--state-root`),
остаётся там, где его создали: запретить это нельзя, не сломав установку
пилота, чей боевой авторитет живёт внутри его репозитория.

## Одна популяция: реестр

`init` и `project init` регистрируют созданный авторитет **при создании**, а не
при первом старте. Раньше регистрировал только старт, и авторитет, который
инициализировали и не запускали, был невидим — единственная причина, по которой
обход диска существовал. Теперь незарегистрированных нет, и монитор показывает
**только реестр**; `--scan-root` остался явным опт-ином для каталогов, где кто-то
создавал авторитеты в обход CLI.

Тест пинит все три свойства — регистрацию обоими `init`, место по умолчанию,
отсутствие обхода без `--scan-root` (`discovery.directories == 0`) — и проверен
вырезанием.

## Чистка, сделанная сразу, по слову владельца

| что | размер |
|---|---|
| пять старых авторитетов в `Application Support/projects` (2–7 сентября) | 36 МиБ |
| 182 мёртвые записи реестра | — |
| пять старых заходов пилота `run7`–`run12` (7 сентября) | 68 МиБ |
| ничей `~/.prifly-state` (8 сентября) | 156K |

Не тронуто: боевой sandbox пилота (336 МиБ, активный) и четыре стенда пакетчика
(11 МиБ) — на них стоят сравнения выпусков. Пилот проверил: потерь нет, ни один
из удалённых ему не был нужен.

Оказалось, что временного мусора на диске уже **не было**: фикстуры под `/tmp` и
scratchpad'ами убрали сами тесты и ОС. Что оставалось — мёртвые указатели в
реестре, которые монитор перечитывал дважды в секунду.

## Наблюдение пилота, вошедшее в решение

macOS чистит `/private/tmp` по возрасту: у него за час исчезли два каталога с
заметками, а у меня — scratchpad сессии, отчего прогон ворот доложил `rc=1` при
воротах, которые не запускались вовсе (код принадлежал редиректу в исчезнувший
каталог — шестой случай на двоих, когда врёт обвязка, а не проверка). **Всё,
что должно пережить сутки, в `/tmp` жить не может** — это довод за `~/.prifly/`,
а не против.

## Гонка в моём коде 0.13.15, пойманная воротами

Горутина, останавливающая монитор при исчезновении авторитета, писала в
`errout` одновременно с основной. В проде это `os.Stderr`, и внешне ничего не
ломалось; под детектором — гонка по контракту `io.Writer`. Горутина теперь
только останавливает сервер, а строка пишется после `Serve`, из владельца
`errout`.

**После обновления перезапустите монитор** — работающий процесс правку не
подхватит, и старый на 7777 так и будет обходить миллион каталогов.
