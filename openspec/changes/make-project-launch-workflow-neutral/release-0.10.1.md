# Выпуск Pri-Fly 0.10.1

Версия утверждена владельцем 2026-09-06 после доклада пилота об именовании
идентификатора решения в анкете. Исходная ветка — `codex/workflow-neutral-plan`,
базовый commit подготовки — `6bbe55a`. Нормативный порядок выпуска остаётся в
`release-distribution/spec.md`; эта запись фиксирует конкретный выпуск.

## Scope

Один исправленный дефект контракта и его нормирование. В `project-questionnaire/3`
идентификатор решения назывался `id` в списках `preflight` и `runtime` и
`decision_id` в `decision_states`; разбор по `.id` возвращал пустые значения
вместо отказа. Приведено к одному имени `id` во всех трёх списках с повышением
версии до `project-questionnaire/4`; та же структура состояний встроена в
launch summary, поэтому он выходит как `project-launch-summary/3`.

`decision_id` не оставлен рядом с `id`. Два имени под одной версией дают два
неразличимых по объявлению документа; читатель прежней формы должен падать на
проверке версии, а не молча получать пустые значения. Решение согласовано с
владельцем пакета AI Factory — единственным известным потребителем этого поля.

Текст generic runner называет версию launch summary, поэтому его рендер изменён.
Прежний рендер заморожен и добавлен в набор признаваемых, так что
`project runners update` заменяет раннеры, установленные версией 0.10.0.

Контракт анкеты до этого выпуска не был нормирован ни одним требованием.
Добавлено требование «Анкета называет решение одним именем во всех списках»
в `cli-protocol` и синхронно в дельту активного change.

Поддержанные release assets и порядок публикации не меняются: `linux/amd64`,
`darwin/arm64`, обе сборки существующим GitHub workflow, macOS нативно, signing
key в protected environment `release`.

**Ломающее изменение для программных читателей.** Клиент, разбирающий
`decision_states[].decision_id` или пинящий строки `project-questionnaire/3` и
`project-launch-summary/2`, потребует правки. Известный потребитель один —
ворота репозитория `prifly-aif-workflows`; его владелец предупреждён заранее и
правит две строки после публикации. Пакет `aif-classic` анкету не разбирает,
поэтому выпущенная версия пакета `v1.11.0` остаётся действующей и релиза не
требует.

Что в этот выпуск не входит: живые UI observations Codex и Claude, живой AIF
pilot, формальные P1/P2 gates. Задачи 3.5 и 4.3 parent change остаются
открытыми; выпуск их не закрывает и 21/24 в 24/24 не превращает.

Известное ограничение перенесено без изменений из 0.10.0: при отказе допуска
уже после подготовки input tree созданные подготовкой файлы могут остаться в
рабочей папке. Дефект `workspace-tree-preparation-rollback` записан в очередь,
его исправление в этом выпуске не заявляется.

## Verification

Ворота прогнаны на кандидате `6bbe55a`.

| Ворота | Где | Результат |
|---|---|---|
| `verify` (`make ci-check` + `make e2e`) | GitHub Actions, run 34034812020 | success |
| `race` (полный race-набор) | GitHub Actions, run 34034894579 | success |
| `go test ./cmd/prifly -count=1` | локально | PASS, 22.890 s |
| `TestGlossaryBindings` | локально | PASS |
| `openspec validate --all --strict --no-interactive` | локально | 20 passed, 0 failed |
| `make schemas-check` | локально | 46/46 совпали |
| `git diff --check`, `gofmt -l ./cmd ./internal` | локально | чисто, пусто |

Объединение `verify` и `race` покрывает тот же набор, что локальный
`make check` плюс `make e2e`, и получено на чистом раннере. Дорогие ворота на
этой машине повторно не запускались.

Отдельно проверен путь обновления раннера настоящей парой бинарников, а не
только закреплёнными digest: бинарник, собранный с `6b0e2f9`, установил раннер
со сводкой `/2`; бинарник кандидата заменил его командой
`project runners update` на всех трёх хостах.

Отдельно проверен фактический вывод: `project questionnaire --json` отдаёт
`schema_version: "project-questionnaire/4"`, каждая запись `decision_states`
несёт непустой `id`, поля `decision_id` в ответе нет; `--prepare` отдаёт
`project-launch-summary/3` с тем же составом идентификаторов.

Новая проверка `questionnaireIdentifiersAgree` читает опубликованный JSON, а не
поля Go. Прежние тесты ходили через структуру и расхождение имён увидеть не
могли — именно поэтому дефект дожил до пилота. Проверка подтверждена негативно
возвратом старого JSON-тега: падают все шесть подтестов.
