# Сохранять naming evidence через передачу claim

**Date:** 2026-11-03 01:23 UTC
**Files:** cmd/prifly/project_start.go, internal/runtime/worktree_naming_source.go и regression tests
**Severity:** high

## Проблема

Новый continuation терял snapshot после передачи исходного claim другому Run.
Legacy source после перехода проекта на profile /5 требовал новые naming inputs.

## Причина

Поиск metadata использовал текущего держателя claim вместо сохранённой связи с source Run.
Общий fallback читал текущую policy без проверки версии source metadata.
Повторная проверка перед start повторяла тот же ошибочный fallback.

## Решение

Read-only поиск сначала проверяет текущего держателя и точный Session.ClaimID.
При отсутствии Session поиск проходит ограниченную цепочку continuation, resume и recovery.
Поиск включает released claims и отказывает при противоречии, цикле или недоступном manifest.
Новый claim копирует snapshot, но не получает владение историческим claim.
Legacy source применяет текущую legacy policy либо обычный hash allocator при новой owned policy.
Prepare и повторная проверка используют одинаковое правило.

## Проверка

Две CLI-регрессии сначала воспроизвели потерю snapshot и project_worktree_input_missing.
После исправления все четыре варианта проходят: retained/released claim и named/hash legacy source.
Unit tests проверяют точный Session.ClaimID, ancestry, независимый fork, ошибки чтения, цикл, предел и противоречие.
Новые сообщения runtime не выводятся: отказ сохраняет типизированный код Fault.

## Предотвращение

Отделять историческое naming evidence от текущего владения ресурсом.
Проверять migration старого source при включении новой project policy.
Дополнительная полезная проверка: повторить цепочку с несколькими реальными handover через resume и recovery.
Не считать прямой continuation достаточной проверкой истории после передачи claim.
