## ADDED Requirements

### Requirement: Runner использует справочник до исследования исходников Core

Поставляемый runner MUST оставлять в основном skill обязательные инварианты запуска, исполнения и отчёта.
Для дополнительных процедур runner MUST читать индекс и нужную страницу поставленного справочника.
После страницы runner MUST использовать текущие `help`, `schema`, `capabilities`, `run next` и диагностику для уточнения доступного поведения.
Для обычной поддержанной операции runner MUST NOT начинать с исследования исходников Pri-Fly.
Если справочник и публичная диагностика не дают ответа, runner MUST явно назвать пробел или предполагаемый дефект.
Исследование Core остаётся допустимым для задачи разработки или диагностики самого Core в пределах полномочий шага.
Это правило MUST NOT ограничивать чтение исходников целевого проекта, когда этого требует задание Run.

#### Scenario: Хосту требуется отправить StepResult

- **WHEN** текущее задание требует typed result, а короткого skill недостаточно
- **THEN** хост читает страницу отчёта, получает актуальный шаблон и схему через публичный CLI и не ищет сериализацию в Go-коде

#### Scenario: Проявился недокументированный отказ

- **WHEN** страница и текущие публичные ответы не объясняют отказ
- **THEN** хост сообщает точный Problem code, версию и недостающее описание вместо предположения о безопасном обходе

### Requirement: Runner обновляет установку перед созданием нового Run

Перед подготовкой каждого нового `project start`, `project continue` или `project recover` runner MUST выполнить явные проверки обновлений binary и установленных upstream workflows.
Для managed binary runner MUST вызвать поддержанный `update`, который проверяет signed stable release и применяет доступное обновление.
Runner MUST использовать точный executable из machine-local конфигурации и повторно получить его версию и capabilities после обновления.
Для workflow runner MUST использовать установленное происхождение и настроенный ref; совпадение авторской версии MUST NOT заменять сравнение upstream commit.
После обновления binary runner MUST проверить и обновить известный runner и справочник, затем прочитать новые инструкции и `PROJECT.md`.
Успешная последовательность MUST предшествовать получению окончательных launch selection, questionnaire и review digest.
Изменение package, inputs, skills или решений после prepare MUST требовать нового prepare и нового подтверждения summary.
Проверка MUST выполняться один раз для одной подготовки нового запуска, без повторения на каждом `run drive` или принятом отчёте.
Изменение входов проверки либо отдельный запрос нового запуска MUST отменять прежний результат проверки.

#### Scenario: Доступны новые binary и workflow bytes

- **WHEN** runner готовит новый Run при доступных разрешённых обновлениях
- **THEN** он обновляет binary, workflows и runner до prepare, перечитывает launches и показывает summary фактически выбранной сборки

#### Scenario: Обновлений нет

- **WHEN** все проверки успешно подтвердили текущие bytes
- **THEN** runner продолжает обычную процедуру выбора и prepare без повторных проверок внутри этого запуска

#### Scenario: Продолжается уже выданный Attempt

- **WHEN** хост исполняет или завершает Attempt существующего Run
- **THEN** runner следует закреплённому заданию и не выполняет эту процедуру обновления посреди Attempt

### Requirement: Неподтверждённая актуальность останавливает новый запуск

При ошибке сети, подписи, installation receipt, unsupported installation, конфликте runner или локальных workflow bytes runner MUST остановить новый запуск.
Он MUST сообщить точную причину и выполненные частичные обновления; неизвестный результат MUST NOT называться актуальностью.
Runner MUST NOT заменять source build, удалять изменённый workflow, сбрасывать рабочее дерево или обходить отказ обновления.
`extend.yaml`, `project/`, `PROJECT.md`, пользовательские файлы и закреплённые Runs MUST сохраняться.
Локальный авторский workflow без upstream origin MUST быть явно назван локальным; runner MUST NOT придумывать ему upstream.
Если для локального workflow требуется внешнее подтверждение версии, новый запуск MUST ждать этого подтверждения.
Закреплённый tag или commit MUST сохраняться. Проверка MUST явно отличать актуальность настроенного ref от наличия нового выпуска вне этого ref.
Переход с закреплённого ref на новый выпуск MUST требовать явного выбора владельца, а затем нового prepare.
Правило относится к host runner; прямые CLI-вызовы MUST NOT получать скрытую сетевую проверку либо автоматическое обновление.
Существующая явная семантика updater и workflow update сохраняется; ownership `release-distribution` и `workflow-and-context` не переносится.

#### Scenario: Сеть недоступна

- **WHEN** runner не может завершить обязательную проверку перед новым запуском
- **THEN** он сообщает ошибку и не создаёт Run, claim либо новый trusted package

#### Scenario: Исходник workflow изменён локально

- **WHEN** `project workflows update` сообщает конфликт локальных bytes
- **THEN** runner сохраняет изменения и останавливается с диагностикой вместо remove/add или принудительной перезаписи

#### Scenario: Workflow закреплён на прежнем tag

- **WHEN** настроенный tag неизменен, а вне него найден новый выпуск
- **THEN** runner сообщает обе версии и запрашивает переход; он не выдаёт неизменность tag за проверку последнего выпуска

#### Scenario: Оператор вызывает CLI напрямую

- **WHEN** оператор явно вызывает `project start` без host runner
- **THEN** команда сохраняет существующую процедуру и не выполняет скрытое обновление
