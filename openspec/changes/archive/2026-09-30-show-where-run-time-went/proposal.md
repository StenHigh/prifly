## Why

Оператор следит за временем Run и хочет понимать, на что и сколько ушло. В
Run пилота `aif:workflow/classic` общее время — «частично: известно 8½ минут,
по часам около 40». Остальное отчёт о времени не объясняет: у каждого шага с
агентом «время исполнителя» — `unavailable, executor_start_not_observed`, хотя
моменты выдачи задания (`session.handed`) и получения отчёта
(`session.reported`) в Run записаны. Самая дорогая часть Run — работа агента —
в отчёте не видна вовсе. Не видно и того, сколько Run ждал, пока агент возьмёт
задание, и сколько ждал ответа на вопрос.

## What Changes

- Отчёт о времени (`run timing`, `/api/timing`, калькулятор `core-timing/4`)
  получает для Attempt assisted-шага три интервала по записанным моментам:
  - `host_pickup` — от выдачи Attempt до `session take`;
  - `host_session` — от выдачи до отчёта;
  - `host_work` — от взятия задания до отчёта, без ожидания ответа на вопрос;
  - `decision_wait` — ожидание ответа на runtime-решение этого Attempt.
- Новая команда `session take --run RUN --attempt ATTEMPT`: host отмечает, что
  взял задание; хранится один раз (`session.taken`, событие
  `attempt.session_taken`), задача называет её в `take_command`. `session task`
  остаётся чтением: запись при чтении упиралась бы в блокировку Run и
  засчитывала бы каждое перечитывание как новое взятие. Без `session take`
  `host_pickup` недоступен, а время до взятия входит в `host_work` с причиной
  `host_take_not_recorded`.
  Качество честное: концы из разных сессий часов — «оценка по часам authority»
  с причиной, как у прочих интервалов. Прежние метрики и их числа не меняются.
- Чтобы ожидание ответа было измеримо, запись журнала решений с `attempt_id` в
  Run на `core-state/41` хранит и момент запроса (`requested`). Для Run,
  запечатанных раньше, `decision_wait` — `unavailable` с причиной, а не ноль.
- Свод по Run: суммы по категориям (`*_sum` на узлах дерева, `executor_sum` и
  `check_executor_sum` для программ и проверок) и `idle` на корне — время, когда
  не шла ни одна попытка и ни одна проверка (например, между остановкой и
  продолжением). Сумма
  категорий не выдаётся за elapsed: интервалы параллельных ветвей
  пересекаются, это сказано рядом с цифрой.
- Монитор: в обзоре Run блок **«Куда ушло время»** — категории с полосой доли
  и таблица стадий по убыванию времени, с числом раундов (повторы
  improve/verify/fix видны как `×3`). В блоке шага — фазы каждого Attempt:
  ждал агента → работал → ждал ответа → приёмка.
- `run status` печатает строку `time` со сводом по категориям.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `observability-publication-reactions`: интервалы assisted-сессии и свод по
  категориям в отчёте о времени.
- `local-run-monitor`: блок «Куда ушло время» и фазы Attempt.

Затрагивает runtime продукта. Владение нормативными источниками не меняется.

## Impact

- `internal/runtime/timing.go` (+ ревизия калькулятора), `decisions.go` /
  `decision_bridge.go` (`requested` на записи, state 41 — общая с
  `record-questions-a-step-answered`), `cmd/prifly/main.go` (`run status`).
- `cmd/prifly/monitor.js`/`.css`, `monitor_ui_test.cjs`.
- Опубликованные схемы: новые поля только в bundle state 41; закрытые не
  меняются. Документация: `examples/troubleshooting.md` (как читать время),
  словарь метрик.
