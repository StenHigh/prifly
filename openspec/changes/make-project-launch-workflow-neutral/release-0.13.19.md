# Выпуск Pri-Fly 0.13.19

Решение владельца: проверять `permitted_effects`. До этого выпуска граница
эффектов шага **называлась и не проверялась**.

## Что было

Пилот на боевом заходе #111: у verify `permitted_effects =
[write_inside_declared_output_slot]`. Он написал патч в checkout во время
verify, сам снял его `git checkout`, чтобы остаться в разрешённом слоте, и
применил в fix. Цена честности — лишний прогон 186 пинов. Движок не заметил бы,
оставь он правку: граница держалась дисциплиной исполнителя. Тот же класс, что
`retryable: false` и `MaxLogicalOperations` без траты — объявленное, чего никто
не исполняет.

## Что стало

При передаче шага **без** `effects.class: workspace_write` движок записывает в
запись передачи отпечаток каждой рабочей копии, которую Run держит по заявке:

```
sha256( git rev-parse HEAD  +  git status --porcelain=v1 --untracked-files=all --no-renames )
```

При `session submit` сверяет. Разошлось — отказ, передача остаётся ожидающей:

```
effect_not_permitted | this step may write only inside its declared output slot, and the
  workspace at <путь> changed while it ran: <пути>. Put the workspace back as it was
  handed over … and report again. If the named paths are byproducts of a build or a
  test run, list them in .gitignore — the mark respects it, and a gate must not be
  given workspace_write to make room for its own cache. Declare effects.class:
  workspace_write only for a step that is meant to change the tree
```

Три выхода, и они не равны: откатить; побочные продукты — в `.gitignore`;
объявить эффект — только шагу, который по замыслу пишет. Третий подсказала
сессия пакетчика, прочитав `effects.go` до тега: с двумя выходами читатель,
увидевший `.pytest_cache`, дал бы гейту `workspace_write` — ровно то, что пакет
запрещает.

Шаг с `workspace_write` не меряется. Игнорируемые файлы в отпечаток не входят.
Отпечаток снимается **дважды** — при передаче и при сдаче, не непрерывно: приём
пилота «подставить базовые версии, прогнать, вернуть» сойдётся, если к сдаче
дерево возвращено.

## Цена: новая версия состояния

Отпечаток живёт в `SessionHandoff` внутри состояния Run, а состояние
декодируется с `DisallowUnknownFields` — старый бинарь упал бы на новом поле.
Поэтому `core-state/29` (и `core-read/29`, `core-next/29`, `core-preview/29`,
`core-step-read/29`) по паттерну routed, с **новым** опубликованным bundle
`effects-session.schema.json` (`urn:prifly:core-effects-session:29`). Старый
`routed-session` сгенерирован заново и сравнён с закоммиченным побайтно — не
тронут. Сессия остаётся `assisted-session/7`: `session task` и `submit` не
изменились ни полем.

Run, созданные до 0.13.19, остаются на своей версии и не проверяются — граница
там по-прежнему в прозе.

## Что поймали ворота, чего я не знал

**Текст раннера закреплён по дайджесту.** Я дописал в инструкцию раннера фразу
про измерение — в базовую литеру, из которой через цепочку `Replacer`
выводятся все восемь замороженных вариантов. Все восемь сдвинулись. По ним
`project runners update` узнаёт, что установил прежний выпуск; сдвинь я их —
обновление отказалось бы. Правило из комментария в коде: «текущий выводится из
замороженного, никогда наоборот». Литера восстановлена побайтно, текст 0.13.18
заморожен как вариант 8, новый текущий выведен из него одной заменой. Вариант 8
у каждого хоста — ровно прежний текущий пин.

## Тест — сценарий пилота буквально

Два шага на одной заявке: `plan` с правом записи, `verify` без. Отпечаток
записан у verify и **не** записан у plan. Патч в checkout → `effect_not_permitted`
с именем файла и пути, передача ожидает. Откат → приём, Run завершается.
Вырезание: снял сверку — «отчёт с изменённым деревом принят».

Пилот проверит на первом заходе с тегом ровно этим сценарием; для стендов
пакетчика ожидание `1 of 9` / `1 of 10` — их Run созданы раньше, версия задним
числом не меняется.
