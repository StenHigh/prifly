## Context

Мотивация и границы — [proposal.md](proposal.md). Новые требования — [delta control-security-ux](specs/control-security-ux/spec.md). Это изменение представления существующих фактов; Go authority и формы ответов остаются прежними.

Исходный аудит выполнен на `60931dc6`. Полные локальные материалы находятся в `.cache/codex-reports/monitor-ux-2026-11-11/`. Они не входят в будущий runtime и не заменяют повторную приёмку. [acceptance.md](acceptance.md) содержит переносимые сценарии без зависимости от старого `/tmp` или прежних Run IDs.

| Поверхность | Доступные данные | Ограничение |
|---|---|---|
| Все виды списка Full | `RunSummary.Board`, включая reasons и next_action | `Board` optional; legacy требует fallback |
| Подробности Full | Существующий `RunView`, Attempts/Sessions, stops, waits, decisions, diagnostics | `/api/run` не получает Board; `MonitorView` не заполняет optional failure |
| Допуск в Full | Отдельное чтение capacity и держателей | Это отдельное наблюдение, не часть атомарного снимка Run |
| Light | `LightCard`, reasons, current_runs, phase, reviews, completion_scope, source freshness | Причина не всегда содержит Run identity; owner identity отсутствует |

Кодовые опоры: `internal/runtime/monitor.go` (`MonitorSummary`, `MonitorView`), `monitor_board.go` (`MonitorReason`), `light_types.go` (`LightCard`), `cmd/prifly/monitor_list.go`. Эти файлы изучены как ограничения; их изменение не требуется.

## Goals / Non-Goals

**Goals:**
- Получать объяснение из уже загруженных данных без дополнительных чтений подробностей каждой карточки.
- Отделить достоверность чтения от состояния исполнения и от приёмки.
- Сохранить рабочую навигацию при уплотнении интерфейса.
- Сделать критерии первого экрана и повторного аудита проверяемыми.

**Non-Goals:**
- Общая новая модель authority, универсальный движок правил или клиентская реконструкция lifecycle.
- Новая очередь внимания, изменение lanes/categories или объединение Full и Light.
- Новая система дизайна, framework, npm-зависимости, producer mappings или новые управляющие возможности.

## Decisions

### D1. Общие нормы, отдельные приватные адаптеры

Общие правила размещаются только в `control-security-ux`. `local-run-monitor` сохраняет правила board/provenance/чтения. Активный Light source set сохраняет grouping, mapping, review и read-only границы. Второй baseline `prifly-light` не создаётся; `SOURCE-OF-TRUTH.md` не объявляет перенос владения.

Full list использует существующий `Board` во всех видах, включая related. Full details получает собственный адаптер уже переданного `RunView`. Light получает адаптер `LightCard`. Функции остаются приватными и чистыми: возвращают текст, scope и допустимые ссылки, не делают fetch и не изменяют входной объект.

Единый универсальный адаптер отвергнут: DTO и гарантии чтения различаются. Общий модуль не добавляется только ради одинаковой формы. Небольшие таблицы подписей и одинаковые поведенческие примеры удерживают согласованность без новой абстракции runtime.

### D2. Разделить сохранённое состояние и акцент причины

Сначала выводится исходный status/outcome выбранного объекта. Следом — главное известное препятствие с его scope. Остальные причины доступны через короткий счётчик и раскрытие. Неопределённость и ограничения не прячутся за активностью другой ветви.

Существующий порядок категорий Full остаётся `terminal → stopped → decision → working → resource → waiting → ready → unknown`. Light сохраняет свою таблицу групп. Порядок визуального акцента внутри блока не пересчитывает категорию, статус, lane или phase.

| Факт | Объяснение / безопасный переход |
|---|---|
| `session.host_state=disconnected` | «Связь с хостом потеряна; исход требует проверки»; данные конкретной Attempt |
| `has_unresolved_effects` / uncertain без точной причины | «Исход не установлен»; доступные обязательства и диагностика |
| Отмена ещё выполняется | «Отмена запрошена»; текущие обязательства, без обещания полного завершения |
| Активное ограничение / resume_required | Записанная причина и условия; следующий шаг не запускает resume |
| Pending decision / waiting_decision | Точный вопрос и последствия; переход к данным решения |
| Записанное ожидание ресурса / допуска | Ресурс или допуск; существующие подробности с точным scope |
| Ready / issued без take | Работа подготовлена или выдана; выполнение не объявляется начатым |
| Failed с однозначным текущим кодом | Понятная подпись; `attempt_deadline_expired` — «Истёк срок попытки»; код сохранён |
| Failed без однозначной причины | «Причина не установлена по текущим данным»; диагностика |
| Completed / partial | Завершённый частичный результат и existing `partialCause`; продолжение остаётся отдельным Run |
| `driver_live=false` | «Активность драйвера не подтверждена»; отсутствие наблюдения не означает потерю host |

`executionRole` проверяет явные состояния сессии до обычного fallback ожидания отчёта. Диагностика выбирается только при доказанной связи с текущей Attempt/StageActivation. Последняя error по времени не является таким доказательством. Ошибка после обработанного retry остаётся исторической. Ошибка другой ветви не становится причиной выбранной Attempt; актуальное препятствие той ветви показывается отдельно с собственным scope.

`session.principal_id` обозначает зарегистрированный host, не личность человека. `Stop.actor_id` обозначает автора Stop, не ответственного за продолжение. Light не синтезирует owner; при недостатке данных отдельная подпись сообщает, что исполнитель не указан.

### D3. Следующий шаг — чтение, а не управление

Используются существующие `workflow` / `facts` / `journal`, раскрытие вопроса или диагностики, история задачи и проверенная ссылка на Run. Значение `reason.action` проходит конечный allowlist вкладок; неизвестное значение ведёт в общие подробности.

Full строит ссылку по source/Run и, где поддержано, существующему node. Light сохраняет `fullLink` с `URLSearchParams`, base URL и prefix. Если aggregate reason нельзя связать с одним из current_runs, открываются детали задачи. Выбор первого или самого нового Run запрещён.

Не добавляются shell-команды, copy-and-run, resume/retry/approve или скрытый fetch команды. Повтор HTTP-чтения разрешён. Нынешний защищённый maintenance Full остаётся отдельным и не переносится в Light.

### D4. Свежесть относится к конкретному экрану

Приватное состояние чтения содержит identity запроса, snapshot этой identity, её ETag, факт успешного чтения и состояние текущего запроса. Это память страницы, без новой записи в authority, browser storage или JSON API. На поверхность хранится один текущий snapshot; новый неограниченный cache истории запросов не добавляется. Существующие ограниченные caches сохраняют свои budgets. Параметры навигации и scroll хранятся отдельно; возврат может повторно прочитать данные.

Identity доски включает endpoint и все фактические параметры запроса: нормализованные фильтры, view, order, page, limit и cursor, где они поддержаны. В Full номер page учитывается отдельно от формы фильтров. Identity подробностей включает source, Run либо task key, а также history cursor. Отдельно загружаемые review/report panes и output сохраняют свой scope, включая identity Attempt или отчёта. Смена identity не наследует успех прежнего экрана.

```text
нет снимка → загрузка → данные / пустой результат
                  └→ ошибка первого чтения
данные → обновление → новый снимок
                  └→ прежний снимок + «данные устарели»
смена запроса → новая identity; поздний ответ прежней identity отброшен
```

В Light нельзя использовать общий `lastSuccess > 0` как доказательство кеша подробностей. В Full нельзя сохранять текст загрузки как основное объяснение после ошибки. Ответ 304 применим только к соответствующему snapshot; иначе выполняется чтение без условного ETag. Истечение cursor сохраняет filters и использует существующее явное обновление страницы данных.

Transport error не превращается в host disconnect. HTTP 200 не делает stale source свежим. `source.last_success_at`, coverage и частичная доступность остаются видимыми. Момент локального чтения не выдаётся за момент события authority.

Сохраняются queryEpoch, отмена прежнего запроса и backoff. Смена identity отменяет только локальное ожидание ответа. Не выполняются очистка authority, повтор шага либо автоматический page reset кроме предусмотренного cursor recovery.

### D5. Компактная композиция без смены default view

Первая строка содержит название интерфейса, краткую свежесть и тему. Ниже остаются поиск, выбранный контекст и сводка counts. Дополнительные фильтры помещаются в disclosure с числом активных фильтров. Они продолжают участвовать в запросе, когда скрыты.

Декоративный баннер Full и вводный блок Light сокращаются так, чтобы не конкурировать с первой карточкой. Сведения о хранилищах, paths, IDs, версиях, времени и количестве Attempts раскрываются по запросу. Обязательные предупреждения о недостоверности не скрываются вместе с декоративным блоком.

```text
Список:      название + свежесть → поиск / фильтры → первый результат
Карточка:   название + состояние → причина [scope] → следующий переход
Подробности: тот же основной блок → другие причины → технические панели
```

На узком экране Full строка таблицы становится вертикальной карточкой с доступными labels. CSS-проверка, требующая `min-width:820px`, заменяется браузерным критерием доступности названия и состояния. Схема сохраняет отдельную горизонтальную прокрутку. Default related view и пользовательский выбор вида не переключаются автоматически.

Light не рендерит большие пустые группы перед результатом поиска. Фильтры групп и counts с областью остаются доступны. Фаза задачи, включая unmapped fallback, остаётся вторичным фактом; название стадии не используется для нового mapping.

На первом входе с репрезентативной короткой карточкой title/status/reason/основной переход помещаются в viewport 390×844 и 1440×900 при 100%. Для длинного текста — wrap и доступное раскрытие, без потери полного accessible name. При возврате приоритет имеет восстановление прежней позиции.

### D6. Polling сохраняет контекст

Сохраняются form names, source/key hash, IDs пагинации, `.light-card`, `.card-title`, `data-card`, `data-key`, `data-focus` и существующие точные Run-ссылки. Если необходима правка внутреннего selector, браузерный тест обновляется с проверкой прежнего действия пользователя, а не удалением сценария.

Full invalidation включает все реально отображаемые признаки наблюдения. Риск `driver_live` при неизменных run_version/event_sequence сначала воспроизводится. Только затем добавляется нужный признак в render stamp. Рендер не сбрасывает focus, раскрытые блоки, страницу и положение.

### D7. Проверки входят в обычные ворота

Существующий `monitor_ui_test.cjs` расширяется наблюдаемыми текстами/ссылками и отрицательными сочетаниями. Для Light добавляется `cmd/prifly/light_ui_test.cjs` без npm-зависимостей. Браузер подтверждает геометрию, keyboard/focus, transport faults и proxy links; DOM regex не доказывает удобство.

Небольшой `make ui-check` запускает оба Node suite. Он входит в `check`, `ci-check` и static job `.github/workflows/verify.yml`. В CI Node 24 задаётся явно; это средство тестирования, не зависимость поставляемого бинарника. `test-changed.py` выбирает нужный suite для `monitor*` и `light*`, а общий fallback не теряет UI-проверки. Контракт выбора проверяет `scripts/test_test_changed.py`.

Целевые browser replay расширяют существующие `verify-monitor-board` и `verify-light`. Они работают на одноразовых native fixtures. Default режим `verify-light` сохраняет performance/typed-review/queue/long-history набор. Новый opt-in режим `--scenario stops` проверяет пять причин на отдельном экспорте `TestMonitorBoardExportFixtures`. Оба режима используют общий owned setup; stop fixtures не меняют состав первой страницы performance-набора. После них повторяется `aif-ui-ux` на exact candidate с прежними 12 check IDs и регрессиями из [acceptance.md](acceptance.md).

Полные ворота — один раз перед коммитом итогового снимка через `make ci-check-once CHECK_CONTEXT=<actual-profile>`. Для staged bytes используется `CHECK_FOR_COMMIT=1`. Race и полный e2e остаются выпускными проверками. При изменении состава gate helper должен инвалидировать прежнее evidence; существующие tests cache inputs сохраняются.

## Risks / Trade-offs

- Неполные данные подробностей → честный unknown вместо дополнительного API или склейки разных cuts.
- Один крупный статус скрывает parallel → сохранить scope и все причины, category не пересчитывать.
- Старый снимок другого фильтра → identity-scoped state, поздний ответ отвергать.
- Скрытые технические поля мешают диагностике → сохранить доступное раскрытие и direct links.
- Избыточные UI logs раскрывают payload → не добавлять production console/telemetry; подробные traces и screenshots сохраняет только test runner.
- Нормы Light ещё в активном change → общий delta не переносит владение и не закрывает release gates.
- Новый `project start` может удалить завершённый claim → до повторного audit сохранить implementation candidate и его ветку вне автоматической очистки; проверить naming/claim в native prepare.

## Migration Plan

1. Реализовать задачи через `prifly-run → aif-classic`, сославшись на этот change.
2. Проверить точные runtime/JSON/replay границы и целевые браузерные сценарии на итоговом кандидате.
3. Выполнить повторный `aif-ui-ux` на сохранённом кандидате и освободить только его owned environment.
4. Перед коммитом выполнить полные ворота для фактических bytes и permission profile. Push не выполнять.

Миграции данных нет. Откат возвращает предыдущие frontend assets и их тестовые изменения, не изменяя authority, saved Run, review evidence или listeners. Merge и archive/sync выполняются отдельным действием владельца. Предыдущая ветка `codex/behavior-preserving-refactor` не переносится и не удаляется этим change.

Roadmap linkage: «Понятный путь до результата и очередь внимания владельца». Этот срез улучшает существующие мониторы; общая очередь и всё направление не объявляются реализованными.
