# Выпуск Pri-Fly 0.13.7

Патч к 0.13.6. Одна правка, и она не про текст отказа, а про **маршрут**:
вопрос не доходил до того, кто знает ответ.

## `capacity set` отвечал про форму команды, когда спрашивали про число

`--capacity 0` получал `invalid_usage: capacity set requires --capacity N
--reason TEXT`. Причина не в тексте: у флага умолчание было **нулём**, поэтому
«флаг не передали» и «передали ноль» были одним и тем же состоянием, и CLI
отвечал про форму команды.

Движок при этом **уже** отвечает по существу и знает диапазон:

```
до:        0 → invalid_usage        | capacity set requires --capacity N --reason TEXT
после:     0 → unqualified_capacity | this build is qualified for 1 to 4 attempts at once
          -1 → unqualified_capacity | то же
           5 → unqualified_capacity | то же
   без флага → invalid_usage        | форма команды, как и должно
```

Диапазон **1..4**, и верхняя граница — свойство сборки, а не константа. Поэтому
дописывать «N ≥ 1» в CLI было бы пересказом чужого знания: правильнее пустить
значение туда, где диапазон живёт.

**Ошибка по дороге, из того же класса.** Первая версия правки использовала
сентинел: умолчание `-1` вместо нуля. Оно чинило ноль и ломало ввод `-1`, который
теперь получал вопрос о форме вместо диапазона. **Сентинел не устраняет путаницу,
а переносит её на выбранное им число.** Правильный вопрос задаётся парсеру
(«был ли флаг задан»), а не значению.

**Как нашлось.** Пилот искал неразрушительную пробу на `capacity_conflict` и
попробовал опустить предел до нуля в выброшенной авторитетке. Потратил три
запуска, выясняя исполнением то, чего отказ не называл. Их формулировка: отказ
верен, а причина в нём не названа, и читатель ищет её пробами.

## Открыто владельцу, по итогам ночи

1. **Граница допуска не наблюдаема, не запуская.** Единственный способ узнать —
   попытаться, а попытка создаёт прогон, который встанет в очередь. Отсюда же:
   неразрушительной пробы на `capacity_conflict` не существует.
2. **Пояснение отказа лежит в двух местах.** `Reject` кладёт текст в `message`,
   `fault` после правки 0.13.3 — в `violations[0].reason` с пустым указателем,
   `flow.Problem` — с настоящим. Внешний признак неправильного поля — непустой
   `reason` рядом с пустым `pointer`. По числу затронутых маршрутов варианты
   выхода не равны: «всегда в `message`» меняет один маршрут, обратный — большинство.
