## Context

Мотивация: proposal.md, раздел Why. Сейчас код устроен так:

- Lowering `prifly-step/1` пропускает только общий список полей;
  `external_write` есть лишь в списке `prifly-step/2`
  (`internal/flow/authoring.go:180`). Объявленный блок выбирает контракт 11
  (`authoring.go:315`), а он на ассистируемой линии.
- Программная линия контрактов: 1–5 и ветка 12, то есть 5 плюс
  `blocked`-выход (`internal/flow/schema.go`, комментарий у
  `StepDefinitionV12`). Контракты с 6 закрепляют ассистируемый исполнитель.
- `compile.go:808-826`: границу требует класс, а класс требует границу, и
  `RepeatableRetryClasses` (`pure`, `idempotent`) отказывает. Тот же набор
  разрешает `technical_retries` (`compile.go:237`).
- `start.go:339` отказывает программе с любым классом, кроме `none` и
  `workspace_write`.
- `driver.go:1659` (`settleWith`) решает `uncertain` только по фактам процесса.
  Класс эффекта шага не участвует. Ассистируемый путь
  (`session_timing.go:378`) делает `uncertain` при любом классе, кроме `none`.
- Возобновление и восстановление отказывают Run с `HasUnresolvedEffects`
  (`recovery.go:290`, `recoverySourceUnsettled`), а `run resolve` закрывает
  только `uncertain`-попытку (`resolve.go:85`). Этот выход уже есть, и новый
  механизм его переиспользует.

## Goals / Non-Goals

**Goals:**
- Правдивый журнал для программы, которая меняет внешнюю систему.
- Retry-класс внешней записи действительно решает, повторит ли движок шаг без
  человека.
- Автор, в том числе ИИ, из справочника, `--help` и отказа понимает, какой
  класс выбрать и что будет при прерывании.

**Non-Goals:**
- Песочница или проверка границы. Программа работает с правами пользователя.
- Протокол дедупликации для `deduplicated` у программы: для программы он
  ведёт себя как `reconcile_required`.
- Любая передача границы в процесс (env, аргументы). Её никто не читает.
- Изменение ассистируемого правила потери сессии.
- ActionIntent/ActionDelivery для программ.

## Decisions

**1. Контракт 14 — ветка от 12, а не следующее звено после 13.**
Контракты 6–13 закрепляют ассистируемый исполнитель, так что программе нужна
своя ветка, как 12. Мутатор v14 = мутаторы до 5, затем v12, затем добавление
поля `external_write` с той же схемой границы, что у v11. Схему границы нужно
переиспользовать, а не копировать, иначе две копии разойдутся (см. память
«две копии, ни одна не авторитетна»). Альтернатива: снять закрепление
исполнителя в новом общем контракте. Отвергнута: это меняет смысл линии и
тянет правку опубликованных мутаторов.

**2. Запрещён только `pure`, а не набор «повторяемых».**
Для `external_write` отказывает `retry_class == "pure"`. `RepeatableRetryClasses`
остаётся как есть: он всё ещё решает, допустимы ли `technical_retries`, и
`idempotent` в нём — ровно то, что нужно. Текст отказа для `pure`: «pure
означает шаг без эффектов; внешняя запись, повтор которой безопасен,
объявляет idempotent». Альтернатива: разрешить `idempotent` только программе.
Отвергнута: заявление автора не зависит от исполнителя, а ассистируемый путь
остаётся консервативным по своей причине (решение 4).

**3. Решение `uncertain` принимается в одном месте, в `settleWith`.**
Условие: шаг — программа, `Effects.Class == "external_write"`,
`RetryClass != "idempotent"`, `outcome.Started`, и попытка закрывается без
принятого результата (`accepted == nil && pending == nil` после всех
проверок, включая отказ приёма и отмену). Тогда исход — та же ветка
`uncertain`, что и сейчас: статус, `HasUnresolvedEffects`, диагностика. Код
диагностики новый: `external_write_unreconciled`, текст называет retry-класс
и `run resolve`. Путь восстановления осиротевших попыток после потери
драйвера проверяется на то, что он тоже проходит через `settleWith`. Если нет,
условие выносится в функцию, которую вызывают оба пути, а не копируется.
Альтернатива: проверять retry-класс на возобновлении
(`recoveryFrontier`). Отвергнута: остановка была бы видна только при попытке
продолжить, `run next` и `run status` показывали бы `failed`, а
`run resolve` не принимает `failed`-попытку. Нужен был бы второй механизм
свидетельства.

**4. Ассистируемый путь не меняется.**
Там `uncertain` возникает потому, что движок не может доказать, что сессия
остановилась, а не из-за класса. `idempotent` этого не доказывает. Справочник
говорит это одной фразой.

**5. Новая версия состояния не нужна.**
`requiresExternalWriteState` уже выбирает состояние внешней записи по
границе в плане и не смотрит на исполнитель. Попытка `uncertain` у программы
в нём допустима. Задача 3.3 проверяет это на Run: Run с программной границей
запечатывается этим состоянием, а старая сборка называет контракт 14 новее
себя (как 91e5dd4 для состояния).

**6. Документация пишется для автора, который читает один файл.**
Каждое место, где автор выбирает класс, содержит одинаковую таблицу из трёх
строк: класс → что происходит при прерывании → когда выбирать. Место
выбирается по тому, откуда автор приходит: справочник шага, строка README,
continuation-guide, troubleshooting, `--help`, текст отказа. Проверка
`TestEveryDeclaredCapabilityIsInTheAuthorIndex` держит строку README. Таблица
в справочнике — предмет ревью.

**7. Найдено при реализации (2026-09-29).**
- *Контракт 14 закрепляет исполнитель схемой, а не проверкой в Go.*
  `executor.operation` в v14 — `const: process`, так же как v6+ закрепляют
  `session`. Схема документирует правило сама, и отдельной ветки в
  `compile.go` не нужно.
- *Плоский Run с программной внешней записью не запускал программу.* Состояние
  внешней записи scoped, а ключ исполнителя при старте выбирался по
  `requiresInvocationState`, который его не знал. В результате исполнитель
  записывался под плоским ключом, читался под scoped, получал нулевой таймаут, и
  попытка умирала `attempt_deadline_expired` до старта. Исправлено в корне:
  `requiresInvocationState` включает `requiresExternalWriteState`.
  Ассистируемая внешняя запись этого не замечала, потому что ассистируемый
  исполнитель не пинится.
- *Отказ возобновления `uncertain` Run называл не ту причину*:
  `recover_source_ineligible` «нужен технически упавший Run». Теперь это
  `recover_source_unsettled` с `run resolve` в тексте. Такой Run становится
  пригодным сразу после свидетельства, и выход нужно назвать.
- *`run status` не называл причину `uncertain` Run.* `failure` выводился только
  для `failed`/`cancelled`, и `run next` предлагал `run.resolve` без причины.
  Теперь `failure` есть и у `uncertain`; форма поля та же, версия чтения не
  меняется. `reason_code` в `run next` — опубликованный enum, туда новый код не
  добавляется.
- *Политика пакета.* `aif-classic` закрепляет `core:policy/local@3.0.0`, которая
  внешнюю запись не допускает. Проектный шаг не может сменить политику
  чужого workflow, поэтому отказ старта при `external_write` называет
  4.0.0. Переход пакета на 4.0.0 — за сессией пакета.

## Risks / Trade-offs

- [Попытка `external_write_unreconciled` держит слот authority до
  `run resolve`, хотя программа доказанно остановилась, и другие Runs этой
  authority ждут] → Это существующая семантика `uncertain`. Освободить слот
  сразу нельзя: `run resolve` освобождает его ещё раз и получил бы
  `slot_conflict`. Угадывать по косвенному признаку, отпущен ли слот, — класс
  дефекта «две копии, ни одна не авторитетна». Шагов с `idempotent` это не
  касается.

- [Автор объявит `idempotent` для неидемпотентной программы, и повтор
  запишет дважды] → Это заявление автора, как и прежде `idempotent` без
  внешней записи. Справочник и отказ для `pure` говорят, что движок его не
  проверяет, и приводят пример «ensure, а не create».
- [`reconcile_required` у программы, которая часто прерывается, заставляет
  человека свидетельствовать каждый раз] → Это назначение класса. Для
  примиряющей себя программы правильный класс — `idempotent`, и справочник
  называет эту развилку.
- [Отказ приёма результата (схема, выход) у `reconcile_required` даёт
  `uncertain`, хотя программа, возможно, ничего не записала] → Движок этого
  не знает. Консервативный исход — свидетельство, а не молчаливый повтор.
  Сценарий покрыт тестом.
- [Сборка до этой версии встречает контракт 14] → Измерено: она отказывает
  при компиляции плана, но текстом `schema_invalid at /schema_version: … the
  declared value is "1"`, который подсказывает понизить шаг. Состояние Run
  прежнее (39), поэтому проверка 91e5dd4 («состояние новее этой сборки») здесь
  не срабатывает. Для 0.13.64 и старше это не исправить. Начиная с этой сборки
  неизвестный контракт шага называется «newer than this build»
  (`unsupported_contract`). Пилоту и сессии пакета: обновить prifly и монитор
  до перехода на контракт 14.

## Migration Plan

Совместимость назад: шаги без `external_write` не меняют байты, прежние Run
не меняются. Пилот после выпуска меняет `tests.yaml` на
`effects: {class: external_write, retry_class: idempotent}` с границей
(например, `system: docker`, `operations: [stack.up, stack.down]`,
`target: <имя стека>`). Значения выбирает пилот, движок их не знает. Проверка
настоящим Run — за пилотом (задача 6.3). Откат: предыдущая сборка отказывает
плану с контрактом 14 по имени, и пилот возвращает `class: none`.
