## Context

Мотивация — в `proposal.md`. Документация живёт в README, examples и OpenSpec
по `release-documentation-layout`; описание справочника не является новой
нормативной спецификацией. Таблица возможностей уже проверяется
`TestEveryDeclaredCapabilityIsInTheAuthorIndex`, но тест не подтверждает,
что читатель найдёт настоящее поле и работающий пример.

На момент предложения `main` — `9df35bb`. Реализация reuse находится в claim
`993e5ca3…` (HEAD `b98064d`), nested recovery — в claim `2eb9330e…`
(HEAD `88b52c3`). Их documentation diff входит в подготовку обновления;
неинтегрированные возможности нельзя описывать как доступные в stable.

## Goals / Non-Goals

**Goals:**

- Дать короткий путь «задача → подходящий пример → необходимые поля → команды
  запуска → ожидаемый результат → ограничения».
- Сохранить универсальность: программа без host и Git остаётся базовым
  примером; совет, решения Run и Git workspace используются по потребности.
- Отличать выбор launch, объявленное решение Run и подтверждение prepared
  summary, а прогресс/вывод программы — от её результата и verdict.

**Non-Goals:**

- Новые возможности движка, поля схемы, автоматический выбор или обязательный
  совет; привязка общих примеров к AI Factory либо issue tracker.
- Пересмотр требований, версия релиза, интеграция claim-веток без отдельного
  решения владельца, запуск отложенной Claude UI-приёмки.

## Decisions

1. **Сначала сверить статус, затем редактировать.** Перед новым project start
   владелец интегрирует предыдущие claims по RULES.md. В начале реализации
   фиксируется получившийся baseline и сравниваются уже внесённые тексты:
   README/AGENTS про reuse и continuation/troubleshooting про recovery.
   Копирование тех же изменений из отчётов породило бы дублирование.

2. **README ведёт к материалам, examples объясняет применение.** В README
   остаются короткие ссылки; `examples/README.md` обновляет описания ревизий
   и маршруты по задачам. Существующая capability-таблица сохраняет точное
   множество `prifly capabilities`. Проверка полей и минимальных контрактов
   проводится по коду, схемам и нормативным источникам; новые публикации
   контрактов ради комментариев не создаются.

3. **Руководство выбора — `examples/authoring/launch-choice-guide.md`.**
   Минимальные snippets показывают `/3` с несколькими launch и их
   `title`/`description`, необязательный соседний `PROJECT.md` с критериями
   и отключением совета. Все ID доступны; точный ID, отказ от совета и
   отсутствие описания задачи допустимы. Пример не вводит YAML-флаг отключения.
   Связанные материалы показывают declared preflight/runtime decisions,
   поддерживаемые нативные инструменты и текстовый fallback. Возможность
   интерфейса и доказанная живая приёмка разделяются; Claude остаётся DEFERRED.

4. **Два учебных дополнения, без большой коллекции похожих пакетов.**
   CSV-пример расширяется небольшой демонстрацией `program-progress/1` и
   явного `live_output`/`output_limit_bytes`; основная преобразующая задача
   и ожидаемый report сохраняются. Для `resumable` ревизии 8 добавляется
   `examples/workflows/resumable-report/`: маленькая программа, управляемый
   неуспешный первый запуск и продолжение с сохранённым принятым результатом.
   Его README показывает исходный и новый Run, что повторяется и что наследуется,
   и точный prepare/start с новым digest. Приёмка идёт без Git и ИИ.
   Внешнюю запись не добавляем ради демонстрации восстановления.

5. **Повторное использование проверок описывается как contributor-процесс.**
   Ссылки и команды сверяются с интегрированным helper; local reuse не заменяет
   release gates на точном SHA. Реальный список проверок учитывает изменённые
   файлы и bytes: правка примера либо документа тоже может отменить прежнее
   evidence. В этом change нет dispatch qualify и выпуска релиза.

## Risks / Trade-offs

- [Статус implementation принят за статус выпуска] → сверить версии по
  установленному/собранному CLI и существующим release records; development
  помечать явно, не переписывать historical evidence.
- [Справочник читается как готовый package] → оставить маркировку references,
  проверять отдельно копируемые runnable examples и ожидаемые outputs.
- [Нативный вопрос обещан там, где tool недоступен] → описать условия host/mode,
  fallback и отложенную Claude приёмку без новых живых тестов провайдера.
- [Новый пример изменяет поведение продукта] → ограничить diff authoring,
  программами примеров и их проверками; дефект runtime оформить отдельно.

## Migration Plan

После подтверждения предложения и интеграции предыдущих claims выполнить
документационный Run `aif-classic`. Сверить baseline, обновить навигацию и
материалы, проверить учебные сценарии на собранном CLI в временных проектах,
затем провести предусмотренные gates один раз для итогового снимка.
Владелец интегрирует новую claim-ветку; change архивируется обычным workflow
без delta specs и без изменения опубликованных контрактов.
