## Why

Чтобы понять, с чем шаг начал работу, человек, следящий за монитором, сегодня
собирает ответ из пяти сырых разделов: `context.inputs` — это id артефактов без
происхождения, ответы листа решений лежат строкой в `session.decision_context`,
промпты видны только как ref'ы в `session.skill_refs`, а откуда пришёл вход,
написано в определении workflow на другом экране. Всё нужное уже сохранено в
Run, но собрать это вместе может только тот, кто знает модель движка. Если шаг
получил не ту задачу, не тот ответ или не тот промпт, человек должен увидеть это
сразу, а не после разбора дерева.

## What Changes

- У выбранного исполнения шага (Attempt) появляется открытый по умолчанию блок
  **«Что получил шаг»** над существующими разделами:
  - **Входы** — каждый порт шага с происхождением: «вход запуска `task`» (с
    заголовком и текстом задачи) или «результат шага `warmup`, порт `handoff`»
    (ссылка на этот шаг и содержимое артефакта по раскрытию);
  - **Решения, переданные агенту** — каждый ответ из `decision_context` сессии с
    названием решения из каталога, выбранным вариантом и источником ответа
    (владелец при запуске, значение проекта по умолчанию, автономная политика);
  - **Вопросы шага** — объявленные runtime-решения, которые задаёт навык шага
    (например, «Apply these improvements?» у `aif-improve` — `improve_apply`,
    или `gate_warnings` у `aif-verify`): текст вопроса и варианты из каталога,
    ответ, кто ответил (заранее при запуске, значение проекта, человек во время
    Run) и когда; запросы, заданные этим Attempt, берутся из `decision_ledger`
    по `attempt_id`, ожидающий вопрос — из `pending_decision`. Вопросы, на
    которые агент ответил сам (в том числе заданные навыком в чате), берутся
    из `question_report` Attempt (change `record-questions-a-step-answered`)
    с ответом и основанием — решение, вход шага, инструкции, человек, суждение
    агента — и подписаны как заявление исполнителя. Для Run, где отчёт не
    записывался, блок так и говорит, а не показывает «вопросов не было»;
  - **Инструкции и навыки** — каждый переданный текст контекста (instructions и
    context/skill refs) с названием, объёмом и полным текстом по раскрытию;
  - **Что шаг должен вернуть** — выходы и их схемы, вердикты, по которым граф
    продолжит, класс эффекта и захватываемые файлы рабочей копии.
- В обзоре Run появляется блок **«Входы и решения запуска»**: значения входов
  запуска с их источником (`effective_configuration`) и все записи
  DecisionSheet — название решения, значение, источник; неприменимые к профилю
  решения названы неприменимыми, а не пропущены молча.
- Существующие разделы, «Конверт исполнения», «Исходные сохранённые данные» и
  всё сырое остаются без изменений — для отладки.
- Ничего не угадывается: если сведение не записано в Run (например, старый Run
  без `decision_context`), блок так и говорит.

Изменение затрагивает продукт (UI локального монитора в `cmd/prifly`), но не
runtime: движок, API монитора, сохранённые Run и опубликованные контракты не
меняются.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `local-run-monitor`: подробности шага и обзор Run получают человекочитаемую
  расшифровку того, что шаг получил и что от него ждут, поверх неизменных
  сырых данных. Владение нормативным источником не меняется.

## Impact

- `cmd/prifly/monitor.js`, `cmd/prifly/monitor.css`: новые блоки, чистые
  функции сборки из `state.run`.
- `cmd/prifly/monitor_ui_test.cjs`: проверки сборки блоков на фикстурах
  assisted- и program-шага, старого Run без `decision_context`, и экранирования.
- `openspec/specs/local-run-monitor/spec.md`: новое требование.
- Нет изменений в `internal/`, схемах, `/api/*` и release evidence.
