## Context

Замер, из которого выросло изменение: шесть стадий завершены, их выходы
запечатаны, три коммита лежат в рабочей копии; седьмая стадия — программа —
упала кодом 126 из-за окружения. Run `failed`, `outcome: null`, `run next`
отвечает `terminal`.

Что в коде на 0.13.33:
- `settleWith` при technical failure ведёт Run по `on_error`, если стадия его
  объявила, иначе делает Run terminal. Второй попытки того же шага не создаёт
  никто.
- `Run.terminal()` закрывает доступ к `resume`, `drive` и отмене.
- `fork` собирает новый Run из `workflow_ref`, `brief_ref`, `inputs` и
  `reuse_refs` источника; стадии он не наследует, граф начинается с входа.
- Выходы завершённых стадий — запечатанные артефакты с ref'ами; они уже
  пригодны как входы, если их есть чем связать.

## Goals / Non-Goals

- Цель: техническая неудача одной стадии перестаёт стоить всей работы Run.
- Не цель: отменять предметный вердикт. `fail` и `needs_revision` — решения о
  работе, а не поломки; повторяется только техническая неудача.
- Не цель: воскрешать права. Повтор проверяет их заново.

## Decisions

### Что именно повторять

- **1. Вторая попытка внутри живого Run.** Стадия объявляет бюджет повторов;
  technical failure не завершает Run, пока бюджет не исчерпан. Дёшево,
  укладывается в существующую формулировку спецификации («technical failed …
  обрабатывается safe retry или on_error») и **предотвращает** случай замера.
  Но Run замера уже терминален — этот вариант его не спасает.
- **2. Fork с точкой входа.** Новый Run наследует запечатанные выходы стадий
  до названной и начинается с неё. Исходный Run остаётся неизменным и
  терминальным — ровно то, что требует правило о fork. Спасает уже упавший
  Run. Дороже: нужно связать выходы источника со входами стадии и доказать,
  что связаны именно они (ref и digest, а не имя стадии).
- **3. Переоткрытие терминального Run.** Дешевле всего на вид и хуже всего по
  сути: «терминальный» перестаёт что-либо значить для всех читателей, а
  журнал получает вторую историю той же стадии.

Рекомендация: **1 и 2 вместе, в этом порядке**. 1 закрывает причину (стадия,
которую можно перезапустить, не убивает Run), 2 закрывает последствие (Run,
который уже умер, не выбрасывает работу). 3 отклонён.

### Границы повтора

- Повторяется только technical failure. Предметный вердикт стадии повтором не
  отменяется.
- Права и ресурсы перепроверяются: claim берётся заново, одобрения и гранты не
  наследуются, незакрытые внешние эффекты остаются обязательствами исходного
  Run.
- Переиспользование выхода — по ref и digest запечатанного артефакта, не по
  имени стадии: иначе повтор молча возьмёт чужие байты.

## Risks / Trade-offs

- Вариант 2 создаёт Run, часть стадий которого не исполнялась. Читатель должен
  видеть это в самом Run, иначе провенанс врёт: понадобится запись о том, что
  стадия унаследована, и от какого Run.
- Бюджет повторов (вариант 1) — ещё одно объявляемое число; без предела повтор
  превращается в бесконечный цикл на стабильно падающей программе.
