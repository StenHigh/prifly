## Why

Владелец хочет вести два Run одного проекта одновременно. Проверка на HEAD
`5f97382` (пробный проект, собранный бинарь) показала: ассистируемые шаги двух
Run уже могут ждать агента одновременно (после `capacity set --capacity 2`), у
каждого Run в режиме `worktree` своя рабочая копия. Мешают три вещи:

1. Шаги-программы разных Run идут строго по очереди: `driver.lock` один на
   authority, и драйвер держит его, пока исполняет программу. `run drive` второго
   Run во время программы первого отказывает `driver_already_active`.
2. `project start` в этот момент теряет причину: отказ приходит как
   `project_start_incomplete` с одним id Run.
3. Ёмкость допуска по умолчанию 1: второй Run встаёт в очередь, пока не сказать
   `capacity set`.

И обратная сторона: снять очередь целиком нельзя. Два прогона тестов или две
проверки одновременно грузят машину до 100 % и мешают друг другу. Нужен способ
сказать «эти шаги не идут одновременно в разных Run», и сказать его должен
проект, а не движок: Pri-Fly не знает, что такое тесты.

## What Changes

- **Драйвер на Run.** Блокировка драйвера своя у каждого Run
  (`driver-<run>.lock`), у authority остаётся общая разделяемая блокировка;
  операции над всем проектом (освобождение рабочей копии, очистка) берут её
  исключительно. Программы разных Run исполняются одновременно.
- **Исключительные ресурсы.** Расширение workflow (`extend.yaml`) объявляет
  ресурс: имя, `limit` (по умолчанию 1) и корневые стадии, которые его держат
  (`resources: {heavy: {limit: 1, stages: [tests, verify]}}`); лимит этой машины
  можно переопределить в `local.yaml`. Имена непрозрачны для движка. Run
  запечатывает привязку и лимиты при старте (состояние 42); попытка допускается,
  только если ресурс держат меньше попыток всей authority, чем лимит её Run,
  иначе отказ `resource_busy` с держателем — попытка не создаётся и допускается
  на следующем `run drive`, как и при занятой ёмкости. Ресурс вызова (`call`)
  наследуют все попытки внутри вызова. Хранилище (версия 7) держит ресурсы
  рядом со слотами допуска и проверяет их в той же транзакции.
- **Видно, кто кого ждёт.** Отказ называет ресурс, лимит и держателя;
  `capacity show` и монитор перечисляют держателей каждого ресурса; монитор
  показывает запечатанную привязку Run. `prifly-run` объясняет хосту, что это
  ожидание, а не сбой.
- **Причина отказа `project start`** — код исходной причины
  (`driver_already_active` и т. д.), а не `project_start_incomplete`.
- **Ёмкость по умолчанию** для новой authority проекта (`project init`) — 2
  (до 4 командой, как и раньше); хранилище и `prifly init` по-прежнему 1.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `runtime-resources`: драйвер одного Run не блокирует другие; допуск попытки
  учитывает объявленные проектом исключительные ресурсы.
- `cli-protocol`: профиль и расширение проекта объявляют ресурсы и их стадии;
  чтение Run называет ожидание ресурса; `project start` передаёт причину отказа.

Затрагивает runtime продукта. Владение нормативными источниками не меняется.

## Impact

- `internal/runtime/engine.go`, `driver.go`, `worktrees.go`, `retention.go`
  (блокировки), `capacity.go`, `internal/local/store.go` (ресурсы в допуске,
  ёмкость по умолчанию), `start.go` (запечатать привязку), новая версия
  состояния для привязки ресурсов в Run.
- `cmd/prifly/project*.go` (профиль /3 `resources`, `local.yaml`, `extend.yaml`
  `stage_resources`, компиляция), `project_start.go` (причина отказа),
  `monitor.js` (ожидание ресурса).
- Опубликованные схемы профиля, расширения, Run — новые версии; прежние не
  меняются.
- Документация: `examples/authoring/project-profile-…`, `extension-…`,
  `examples/README.md` (строка возможности), `troubleshooting.md`, словарь.
