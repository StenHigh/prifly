## Context

Мотивация и scope — [proposal.md](proposal.md); требования — [cli-protocol](specs/cli-protocol/spec.md), [control-security-ux](specs/control-security-ux/spec.md) и [workflow-and-context](specs/workflow-and-context/spec.md).

`project workflows --json` уже возвращает `project-workflows/1` с exact ID, title, description, source и объявленными inputs. `readProjectProfile` требует непустые title/description, но это не гарантирует достаточное описание назначения. Список читает локальные объявления; полная пригодность выбранного запуска всё равно проверяется анкетой и prepare.

Текущий generated runner создаётся в `cmd/prifly/project.go`; установленный `SKILL.md` — его продукт, а не место ручной правки. В разделе Start сказано показать список и ждать. Native tool прямо назван в разделе Declared questions для runtime wait; прежние инструкции общего finite выбора сохранились в frozen variants. Скриншот пользователя подтверждает текстовый выбор launch в одном диалоге, но не показывает доступные tools или режим, поэтому конкретная причина того диалога остаётся непроверенной.

Runner обслуживает `codex-cli`, `codex-app` и `claude-code`; `PROJECT.md` читается рядом с ним и сохраняется при update. При реализации нужно сохранить exact bytes всех прежних variants: часть исторических строк сейчас производна от других templates, и правка нижнего template способна незаметно изменить узнаваемые исторические тексты.

## Goals / Non-Goals

**Goals:**

- Разделить три действия: условный совет по назначению, явный выбор launch и подтверждение подготовленного выполнения.
- Использовать существующие данные и инструкции проекта, не требуя изменения каждого workflow.
- Вернуть прямое указание на применимый native question tool в начало процедуры выбора и анкету, с честным ожиданием ответа и текстовым fallback.
- Проверить доставку bytes, действующий CLI protocol и наблюдаемое поведение hosts раздельно.

**Non-Goals:**

- Classifier в CLI/runtime, автоматический selector, triage Run, новый model step или provider invocation.
- Новые schema fields, настройки workflow, обязательный TaskInput/RunBrief для file-only сценариев или новый универсальный task adapter.
- Изменение графов, admission, effects, claims, outputs, DecisionCatalog recommendations либо model profiles.
- Установка workflow из каталога по совету, переключение режима host ради UI, новый UI Pri-Fly либо обход ограничения инструмента предпочтений для approval.

## Decisions

### 1. Совет — условная часть host-диалога, а не стадия workflow

Точка рекомендации находится между read-only списком launch и выбором ID. Наличие нескольких launch само по себе не означает полезность совета: нужен выбор по описанной задаче и достаточные основания в назначениях. Точный ID, единственный launch и пропуск совета обходят подбор. Если выбор по задаче уместен, но descriptions не позволяют различить назначения, host коротко сообщает недостаток сведений.

`PROJECT.md` может уточнить критерии, отключить совет целиком или исключить из рекомендаций отдельные launch, например технические сценарии с заранее заданным назначением. Исключённый launch остаётся в selectable списке и доступен по exact ID. Для уже известного ID не нужен повторный выбор. Отсутствие `PROJECT.md` не означает обязательную рекомендацию: действует общая проверка применимости. Для workflow без предмета работы свободное описание задачи не становится обязательным.

Альтернативы: обязательная рекомендация для каждого запуска навязывает лишний шаг; флаг в YAML создаёт новую настройку для проблемы host-диалога; отдельный triage Run требует выбора до самого выбора. В первой версии они не нужны.

### 2. Единица совета — exact объявленный launch

Основания берутся из текущего `project workflows --json` и overlay. Не используем имя пакета, слово `fix` в ID, удалённый каталог или знания о конкретном AIF graph как замену description. Авторы могут объяснить условия использования и ограничения в существующем description; новая обязательная форма описания не вводится.

Совет называет ID/название и одну причину, отделяя неизвестное. Он не обещает пригодность input bindings, программ, окружения или admission до prepare. Description служит данными о назначении, а текст из задачи не разрешает запуск, установку или расширение effects.

Альтернатива — новые `selection_rules`, confidence или tags. Их полезность не установлена, а scope прямо исключает новые поля. Неоднозначность в этой версии остаётся видимой человеку.

### 3. Нативный выбор независим от рекомендации

Общее правило конечных вопросов размещается прямо в Start до первого launch choice и применяется к объявленным finite вопросам анкеты. В template задаём вызов фактически доступного и применимого инструмента, а не только требование «показать варианты».

| Host | Выбор инструмента | Ожидание |
|---|---|---|
| Codex CLI / app | `request_user_input`, когда он предоставлен и допускает вопрос в текущем режиме; иначе применимый `request_user_input_async`, если предоставлен | Blocking result либо отдельный пользовательский ответ async; receipt показа недостаточен |
| Claude Code | Предоставленный `AskUserQuestion` | Ответ пользователя |
| Любой host без применимого tool | Один явный текстовый вопрос | Явный ответ; никакого guessed default |

Это выбор по фактическому tool contract, не обещание наличия конкретного инструмента во всех версиях host. В текущей сессии `request_user_input` ограничен Plan mode, а `request_user_input_async` предоставляет native вопросы с options; эти сведения не переносятся как универсальный контракт всех Codex установок. [Официальная документация](https://developers.openai.com/api/docs/guides/async-tool-calling#add-a-tool-to-ask-the-user-for-input) описывает общий async принцип и подчёркивает, что имя/schema такого инструмента принадлежат приложению, а не встроенному Responses API; доступность Codex устанавливаем по реальной сессии.

Options содержат exact launch mapping, краткое назначение и только реальные альтернативы. При достаточном совете рекомендованный вариант обозначается; без него не придумываем рекомендованный launch. Один selectable launch может быть показан с реальной возможностью отложить выбор, если tool требует несколько options. Большой список разбивается по текущему лимиту инструмента, с доступом к каждому ID, возвратом и отказом. Свободный ответ, который допускает tool, также проверяется по текущему списку; неизвестный ID не заменяется автоматически.

Асинхронный вызов не открывает путь к анкете выбранного launch до ответа. Можно вести независимую read-only работу, но нельзя выбрать ID из preselection, dismissal или таймаута. Native tool предпочтений не используется для авторизации executable effects, если его контракт запрещает approval: подтверждение summary сохраняет отдельный допустимый канал. Не переключаем host в Plan mode и не имитируем кнопки Markdown.

Альтернатива — один жёстко заданный `request_user_input` для всех Codex контекстов — даёт текстовый fallback даже при доступном другом native tool. Автоматическая смена режима затрагивает настройки пользователя и здесь исключена.

### 4. Задача сохраняется по контракту выбранного workflow

Исходный task text и ссылки остаются предметом работы. Отдельное объяснение совета не заменяет этот текст. После выбора questionnaire определяет реальные inputs: используем переданный файл/ref либо упаковку исходного текста в объявленную schema, не изобретая universal port `task`. Если соответствие неясно, уточняем его; workflow, который требует только файлы, получает только заявленные inputs.

Нет нового обязательного промежуточного artifact, provider adapter или `task prepare` для каждого запуска. Предстартовый совет не записывается как runtime DecisionRecord и не расширяет DecisionCatalog. Selected ID не подтверждает prepared summary; existing digest checks, typed validation, standing answers и executable authorization сохраняются.

### 5. Upgrade сохраняет выпущенные инструкции

Перед изменением current rendering фиксируем предыдущие exact generated тексты для всех hosts в accepted variants. Изменение не должно переопределить frozen bytes через общий предок шаблонов; frozen hash tests проверяются до обновления только current pins. Generated файлы обновляются существующим `project runners update`, overlay сохраняется байт-в-байт, custom edits по-прежнему отказываются атомарно.

В реализации не правим installed skills вручную ради обхода recognition. Отдельный `PROJECT.md` остаётся местом проектных критериев. Entry-point документация показывает назначение launch в существующем description и необязательный совет без новой capability runtime/schema.

### 6. Проверка не подменяет диалог проверкой строк

Механические tests покрывают current text, host substitution, все released variants, overlay и CLI guards. Их зелёный результат не доказывает, что модель вызвала tool или дождалась ответа. Для поведения нужен отдельный воспроизводимый сценарий реального host с записью versions, входного сообщения, установленных runner bytes, объявленных launch, доступных tools/режима, tool calls, ответа и команды, которую host выполнил после ответа.

Основная generic fixture имеет два launch с разными назначениями и input formats; отдельный launch получает отключение совета через overlay. Имена заменяются и намеренно расходятся с подсказками назначения. Реальные workspace/execution эффекты в fixture минимальны. Pre-choice snapshot проверяет отсутствие нового package, claim, Run и `project start`; после выбора альтернативы проверяется именно её questionnaire и сохранение task text. Для отсутствующего tool нужен проверенный режим/host без него: нельзя выдать scripted отсутствие за наблюдение реального UI.

Runtime UI observations закрываются по каждому host отдельно. Необходимые случаи: совет с выбором альтернативы; native выбор без совета; async receipt без ответа; точный и неизвестный ID; отсутствие задачи и отказ от совета; неоднозначные descriptions; один/ноль launch; список сверх лимита; перенос задачи между разными schemas; file-only запуск. Табличная запись связывает их с tasks и указывает непроверенное явно. Новый набор может жить в change как актуальное evidence реализации; прошлые release records не переписываются.

## Risks / Trade-offs

- [Общие descriptions дают произвольный совет] → проверка достаточности основания и отсутствие совета при неоднозначности; fixture с переименованными ID.
- [PROJECT.md отключает совет, а host скрывает launch] → native/text выбор всё равно содержит все объявления; отдельная проверка явного выбора исключённого launch.
- [Tool есть в списке, но запрещён текущим режимом или для approval] → учитывать контракт каждого вопроса, использовать применимый вариант или честный текстовый fallback; не менять режим.
- [Async receipt ошибочно принят за ответ] → отдельный этап наблюдения до ответа с отсутствием зависимых команд и mutation.
- [Правка общего template меняет исторические bytes] → freeze предыдущего current rendering и проверка всех pinned released variants.
- [Зелёные text tests выданы за host acceptance] → отдельное evidence фактических calls/UI; недоступный host остаётся непроверенным.
- [Поздний sync открытого `make-project-launch-workflow-neutral` перезапишет уточнения] → перед archive/sync сверить пересекающиеся требования host entry points, neutral runner и exact launch; сохранять более полное актуальное поведение без переписывания его historical evidence.

## Migration Plan

1. Реализовать изменение current runner и tests, сохранив previous/frozen variants; обновить действующие справочники.
2. Проверить CLI guards, upgrade и реальные host-диалоги. Выпуск и обновление проектов выполняются обычным процессом; новая версия public schemas не требуется.
3. В проекте владелец выполняет `project runners update` и проверяет diff generated skills; `PROJECT.md` сохраняется. Старые Runs и workflow packages не мигрируют.
4. При archive/sync уточнить три существующих source sets и проверить пересечения с активными deltas. Ownership-карта сохраняется; milestone/gate не закрывается одним document check.
5. Для отката вернуть reviewed generated skill из предыдущего коммита проекта; не сбрасывать authority, claims или Runs. При следующем upgrade предыдущие exact bytes остаются узнаваемыми.

## Toolchain update

Дополнительный scope явно задан владельцем 2026-10-12 во время apply: обновить Go до последней стабильной версии. [Официальный список](https://go.dev/dl/?mode=json) на эту дату называет Go 1.27.2. Первый baseline `ci-check` выполнил tests, vet, formatting, refusal и staticcheck на Go 1.27.0, но остановился на `vuln-check`: сканер указал исправление десяти достижимых уязвимостей стандартной библиотеки в Go 1.27.2. Это исходное состояние, а не следствие правки runner.

Обновляем установленный Go и локальный `.tools/go` проекта, затем в реализации поднимаем `go.mod` до `go 1.27.2`. Verify, qualify и release уже читают версию из `go.mod`; второго pin в workflows не создаём. Проверки worktree используют явный путь к исправленному toolchain, поскольку `.tools` gitignored и в claim checkout отсутствует. Ворота выполняются без исключений для vulnerability findings; старые release records и public schemas не правятся.

На исправленном Go старый staticcheck `v0.8.1` не прочитал export data version 5. Опубликованной более новой стабильной версии нет; [upstream](https://github.com/dominikh/go-tools/blob/452d5bb86b45416c35891262f6a11dbd6a970117/go.mod) уже обновил загрузчик. Для этого совместимого development tool закрепляем точный `v0.7.0-0.dev.0.20261009230814-452d5bb86b45` вместо плавающего `master`/`latest`; это development snapshot анализатора, а не prerelease Go. `govulncheck` обновляем до опубликованного стабильного `v1.9.0`. Обе версии должны пройти фактическую проверку на целевом Go, без исключения checks или runtime-зависимостей на эти tools.
