## Context

Факты проверены агентом на HEAD `5f97382`: `driverLock` — один файл
`driver.lock` на authority (`engine.go`), `Drive` держит его весь вызов и
возвращается при передаче задания хосту, но программу исполняет внутри вызова;
`ReleaseWorktree` и очистка берут тот же замок; ёмкость — `slot_capacity DEFAULT
1` (`store.go`), потолок 4; допуск — слоты authority в SQLite, CAS на запись.

## Goals / Non-Goals

**Goals:** программы разных Run идут одновременно; проект ограничивает, какие
стадии разных Run не пересекаются; ожидание видно.

**Non-Goals:** распределение по CPU или приоритеты; ограничение внутри одного
Run (там есть `max_parallelism`); знание движка о тестах.

## Decisions

1. **Замки.** `driver-<run>.lock` исключительно для драйвера Run +
   `driver.lock` authority разделяемо у каждого драйвера; освобождение рабочей
   копии и очистка берут `driver.lock` исключительно. Живость драйвера Run —
   по файлу Run. Запись состояния уже сериализована транзакциями SQLite с CAS
   версии Run; гонки двух драйверов проверяются race-тестом двух Run.
2. **Ресурс — лимит на активные попытки, а не на стадии.** Держится от допуска
   попытки до её закрытия, у ассистируемой — всё время у хоста. Хранится как
   слоты с меткой ресурса рядом с общей ёмкостью; допуск проверяет оба в одной
   транзакции.
3. **Где объявлено.** Имя, лимит и стадии — `extend.yaml` workflow (стадии —
   знание workflow; раздел добавлен в схему extension/1, как раньше `answers`
   и `references`), переопределение лимита — `local.yaml` (про эту машину).
   Профиль проекта не менялся: новая версия профиля не нужна. Движок получает
   готовую привязку «стадия → ресурсы» и лимиты при старте и запечатывает в Run;
   допуск проверяет лимит своего Run — двух источников лимита нет.
6. **Ожидание — как у ёмкости.** Отказ `resource_busy` не создаёт попытку;
   её допускает следующий `run drive` (хост повторяет его, как при
   `capacity_conflict`). Очередь честности для ресурса не ведётся: кто первым
   повторит после освобождения, тот и займёт.
4. **Вызов.** Ресурс стадии `call` наследуют все попытки дочерних вызовов:
   `verify` в aif-classic — вызов, а тесты идут в его шаге.
5. **Версии.** Привязка ресурсов в Run — новая версия состояния; профиль
   проекта и расширение — новые версии авторинга, прежние принимаются без
   ресурсов.

## Risks / Trade-offs

- [Два драйвера пишут в одну SQLite] → уже сериализовано; добавляется
  race-тест двух Run с программами.
- [Попытка, ждущая ресурс, держит общий слот ёмкости] → ресурс проверяется до
  слота ёмкости, чтобы ожидающая не отнимала место у других.
- [Лимит authority задаёт последний старт] → записано в `capacity show`;
  расхождение профилей двух запусков видно по источнику лимита.
