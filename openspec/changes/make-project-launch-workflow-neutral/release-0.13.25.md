# Выпуск Pri-Fly 0.13.25

Пилот переехал на 0.13.24 и упёрся в движок ровно там, где п.1 карты
(шаг-программа) должен был закрыть его `tests`: по коду 0.13.24, не по памяти.

## Что было

1. Процесс-шаг не получал пути к рабочей копии Run'а: `ExecutionEnvelope.claims`
   — только `{id, generation}`, `context.json` несёт `claim_id`, но не путь,
   cwd — scratch попытки. Ассистируемый шаг путь получает
   (`task.repository_workspace`), программа — нет. Восстанавливать его по
   именам каталогов — обход.
2. Окружение программы — `PATH=/usr/bin:/bin`, `LANG`, `TMPDIR`, `PRIFLY_*`;
   php/composer/git проекта живут в `/opt/homebrew` и `/Applications/ServBay`,
   и единственный путь к ним — абсолютные пути в общем `extend.yaml`, то есть
   машинно-локальное в общем файле. У `preflight` это решено окружением
   оператора; у шагов-программ слота не было.

Плюс два пробела, найденные по ходу: `workflows add` ставил upstream-`project/`
молча (отказ жил только в `update`); read-only анкета отказывала `--host`,
который `--prepare` требует.

## Что стало

**Путь рабочей копии — в окружении программы.** Run, который держит ровно
одну активную claim, отдаёт процесс-шагу `PRIFLY_REPOSITORY_WORKSPACE` и
`PRIFLY_CLAIM_ID` рядом с `PRIFLY_SOCKET` и `PRIFLY_CONTEXT_FILE` — тем же
значением, что `repository_workspace` у ассистируемого. Не в `context.json`:
это опубликованный контракт (`local-context/1`, `/2`), новая версия ради
одного поля — не та цена; переменные окружения и есть канал фактов процесса.

**И та же мера, что у хоста.** Шаг без `effects.class: workspace_write` под
состоянием с проверкой эффектов измеряется по метке рабочей копии до запуска
и после выхода программы: изменилось — попытка завершается
`effect_not_permitted`, диагностика называет пути и рабочую копию, маршрут —
по `on_error`. Тест: программа, которая только читает — `completed`, в
результате путь claim'а; программа, оставившая файл — `failed`, диагностика
называет `program-wrote.txt`. Оба разреза красные на своих строках.

**Окружение машины — рядом с бинарём.** `prifly project local set --env
NAME=VALUE` (повторяемо) пишет `environment` в ignored `local.yaml`; имена
`PRIFLY_*` — отказ. На старте оно ложится поверх чистого окружения у каждой
программы запуска (пакетной и проектной — на этой машине обе машинно-связаны),
`--prepare` показывает его у каждой программы (`execution[].environment`) и
учитывает в `configuration_digest`: сменил окружение — пересмотри. Разрез:
пустое окружение вместо заданного — красный.

**Upstream-`project/` — отказ и на `add`.** Проверка перенесена в общую для
`add` и `update` проверку upstream-дерева, до установки и подмены; `compile`
не отказывает никогда — там `project/` и есть место проекта.

**Read-only анкета принимает `--host`** для симметрии с `--prepare`.

## Для пилота

`tests` как шаг-программа в `project/steps/` с привязкой в `extend.yaml`:
скрипт читает `PRIFLY_REPOSITORY_WORKSPACE`, гоняет контур, снимает
`measured_tree`, пишет выход по схеме порта; `PATH`/`APP_ENV` — через
`project local set --env`. Кэши — в `.gitignore`, иначе первый же прогон
получит `effect_not_permitted` (метка его уважает). `merge-request` — тем же
путём.

## Ворота

`make check` (race), `make e2e`, CI `verify`.
