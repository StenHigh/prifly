# Выпуск Pri-Fly 0.13.34

Тег на `0fd39d4`. Два OpenSpec-изменения одним выпуском
(`say-what-the-program-gets-and-what-it-left`, `run-a-failed-stage-again`),
оба — по боевому заходу зависимой сессии на опубликованной 0.13.33. Владелец в
отъезде и передал ведение разработки этой сессии; решения этого выпуска
приняты здесь и названы ниже.

## Что было

Заход прошёл шесть шагов, положил три коммита в рабочую копию и упал на
седьмом, программном: программе тестов не досталось пароля БД. Пароль объявили
через `--env-from` **при уже идущем Run**, а окружение программ запечатано
стартом, поэтому объявление до этого Run не доехало — и не могло. Всё, что
здесь неправильно, — молчание:

- ни `project local set`, ни `run drive` не сказали, что открытый Run поедет со
  старым окружением;
- увидеть, что именно получит программа, было нечем: `run status` намеренно
  обнуляет `executors`, а другого ответа не существовало;
- отказ `nonzero_exit` сказал «inspect recorded evidence», не назвав ни кода
  выхода, ни того, что собственного вывода программы движок не хранит;
- Run стал терминальным, и повторить одну стадию было нечем: `resume` к
  терминальному неприменим, `fork` начинает новый Run с входа графа.

## Что стало

- `run next` у готовой программной стадии несёт `program_environment`: имена
  всех переменных и, для значения, читаемого при запуске, место, откуда оно
  берётся. Никогда значение. Ответ читается из конфигурации, которую **этот**
  Run запечатал, поэтому настройка, изменённая после старта, видимо не входит
  в него. Контракт `core-next/33`.
- `project local set` печатает в stderr, что правка относится к следующему
  запуску, а не к уже идущим Run.
- Отказ ненулевого выхода называет код («the program exited 126») и говорит,
  что вывода программы движок не хранит — только код, причину остановки и
  тайминги.
- `run reopen RUN --expected-version N --reason TEXT` возвращает в работу
  стадию, на которой Run сломался технически и не достиг ни одного outcome.
  Завершённые стадии остаются завершёнными, их выходы запечатаны; стадия идёт
  новой Attempt того же StepInstance, неудачная остаётся в записи; права
  берутся заново при следующем admission. Run, достигший outcome — включая
  `rejected` после предметного вердикта, — отказывает `not_a_broken_run`.
- `WorkflowRevision` версии 5: шаговая стадия объявляет `technical_retries`
  (1..8), и движок сам берёт новую попытку того же шага, пока бюджет не
  исчерпан. Объявить можно только там, где автор шага разрешил повтор
  (`retry_class` `pure` или `idempotent`); иначе компиляция отказывает
  `unsupported_retries` и называет класс. Предметный вердикт повтором не
  отменяется.
- Записи в `examples/troubleshooting.md`: запечатанное окружение, `nonzero_exit`
  и что делать с уже упавшим Run.

## Решение о версиях, принятое в этом выпуске

Список версий состояния в документе способностей ограничен 32 записями, и этот
билд перечисляет ровно 32. Тридцать третья сделала бы наш документ невалидным
против каждого опубликованного bundle, включая те, что этот предел объявили.
Поэтому обе возможности сделаны без новой версии состояния: 33 — семейство
только ответа (`core-next/33`), а бюджет повторов едет в запечатанном плане,
не в состоянии Run. Владелец разрешил не беспокоиться о совместимости, раз
пользуемся инструментом только мы; предел всё равно не поднимался, потому что
не понадобилось. Следующей возможности, которой действительно нужна версия
состояния, придётся решать это отдельно.

## Проверено на опубликованном бинаре

После `prifly update` → `0.13.34`: `workflow_definition_versions` содержит
`"5"`, способности называют `declared_technical_retries` и
`program_environment_named`, `run reopen` стоит в справке, списки версий
состояния и чтения остались по 32 записи. Живого прогона на этой сборке не
делалось: его делает зависимая сессия на своём стенде — это и есть проверка,
ради которой выпуск торопили.
