Параллельны 617 из 654 тестов движка и 923 теста во всех пакетах. Остальные
45 тестов движка последовательны по причине: `t.Setenv` (переменные процесса),
`synctest`, дельта общего счётчика (`planCompilations`, `decisionValueChecks`,
`schemaWorkerRuns`); вместе они занимают ~15 с. Остаток — CPU: 293 с работы на 8
ядер, тесты запускают SQLite, git и дочерние процессы.

Параллельность вскрыла два настоящих дефекта движка, не тестов:
- `run drive` получал ложный `driver_already_active`, если в тот же момент
  чтение Run (монитор опрашивает каждые 1,5 с) проверяло живость драйвера
  разделяемой блокировкой `driver.lock`. Исключительная блокировка теперь
  повторяется 250 мс (`driverLockProbeGrace`); тест
  `TestAReadersProbeDoesNotRefuseADriver` красный без этого.
- Блокировка `installation.json` (обычное открытие и очистка) получала ложный
  `storage_busy`, пока дочерний процесс между fork и exec ещё держал копию
  только что отпущенного дескриптора. То же окно повторов.
Один тест был чувствителен ко времени: программе с таймаутом 300 мс под
нагрузкой не хватало времени стартовать; таймаут 2 с, подтесты параллельны.

3.2 — разбиение `internal/runtime` на подпакеты не сделано, по причинам:
- опубликованные bundles называют определения `<пакет>_<Тип>`
  (`cmd/schema-gen`: `path.Base(t.PkgPath()) + "_" + t.Name()`), и перенос
  `Run`, `Attempt` и соседей в подпакет переименовал бы `runtime_Run` в
  замороженных схемах;
- словарь связывает термины с `runtime.<Тип>` (`TestGlossaryBindings`);
- после параллельности полный прогон пакета упирается в CPU, а не в
  последовательность: дробление не сократит его, а для `make test-changed`
  почти любая правка движка всё равно затрагивает модель `Run`, которую
  импортирует всё.
Выгода — только для правок в листовом коде, цена — переименование опубликованных
контрактов. Не делаем.
