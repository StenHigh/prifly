# Выпуск Pri-Fly 0.12.1

Патч к 0.12.0, выпущенному тем же днём. Исправляет регрессию, которая делала
`project compile` невозможным для **всех** существующих `extend.yaml`, и вместе
с ней более старый дефект того же участка, найденный по подсказке пилота.

## Что чинится

**Паника вместо отказа при чтении расширения.** `cmd/prifly/project.go`:
значение `impossible_verdicts` читалось утверждением типа без проверки, и
отсутствие ключа — то есть любой файл, написанный до 0.12.0, — валило процесс
с трассой стека вместо конверта Problem. Ни кода, ни `safe_next_actions`.

Радиус: каждый `extend.yaml` с расширением. Других не существует — поле
появилось в 0.12.0. Нашла сессия `prifly-aif-workflows` в течение часа после
публикации, воспроизведение минимальное.

Починка шире доклада: отсутствие ключа — обычный случай (пустой список), но
непустое не-список значение теперь **отвергается явно**
(`project_extension_invalid: … impossible_verdicts must be a list of StepResult
verdicts`), а не игнорируется молча.

**Вставка, выходящая из ранее вставленного шага, отказывала неправдой.**
Вставленный шаг клал маршруты в `map[string]string`, тогда как авторские шаги
несут `map[string]any`; поиск ребра при следующей вставке такие карты
пропускал. Итог — `project_extension_route_missing: A → B` для ребра, которое
есть. Дефект старше 0.12.0 и к нему отношения не имеет; найден потому, что
пилот прислал свой настоящий `extend.yaml` и назвал эту форму хрупкой. Его
собственный файл её не задевал: обе вставки выходят из авторского шага. Ровно
следующий шаг в их очереди задел бы.

Отказ, говорящий неправду, здесь хуже паники: паника видна сразу, а этот увёл
бы автора искать ошибку в своём файле и обходить несуществующее ограничение.
Теперь вставленный шаг неотличим от авторского по форме маршрутов.

## Почему обе прошли ворота 0.12.0

Ни один тест не держал форму файла, которой пользуются все.

- `TestExtensionDeclaringImpossibleVerdictsRaisesTheRevision` имеет случай
  «silent» — расширение без объявления — и он был зелёным, потому что строит
  структуру `projectWorkflowExtension` напрямую и парсер не вызывает. Дефект
  жил слоем ниже.
- Все фикстуры `extend.yaml` в тестах были обновлены под новый ключ вместе с
  изменением, так что прежняя форма не осталась ни в одной.
- Вставка, выходящая из вставленного шага, не проверялась нигде.

Формулировка, под которой это стоит запомнить, принадлежит сессии пилота:
**правило, которое держится только на примере, его породившем, — не правило.**
С этой стороны: проверка, которая держится на форме файла, придуманной
автором, не проверяет форму, которой пользуются.

Новые проверки идут через настоящий YAML и настоящую вставку и включают файл
пилота дословно: два расширения, второе нацелено в ребро, созданное первым,
рядом `exclude` и `settings` вложенных воркфлоу, ни одного объявления
`impossible_verdicts`. Плюс файл без ключа `extensions`, файл с
`extensions: []`, не-список значением и чужое имя вердикта. Обе проверки
проверены на отрицание: на невыправленном коде первая падает той же паникой,
вторая — тем самым ложным `route_missing`.

## Что НЕ входит

Подъём ревизии до v4 из расширения проекта остаётся как есть: `extend.yaml`
проекта переводит на v4 весь скомпилированный workflow, включая узлы пакета,
и закрыть недостающие вердикты может только автор пакета. Владелец проекта из
этого сам не выйдет. Это развилка проектного решения, а не строка патча, и она
вынесена владельцу отдельно.
