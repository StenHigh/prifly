# Выпуск Pri-Fly 0.13.4

Патч к 0.13.3. Одна находка пилота на живом заходе и один пробел контракта,
который эту находку три раза мешал обсудить.

## Метрика не молчала — она утверждала неправду

`dispatch_latency` на попытке строилась интервалом **всегда**. При
`Started == nil` концом интервала подставлялось время отчёта (`as_of`), и
метрика помечалась открытой. У завершённой попытки это давало:

```
quality: unavailable   is_open: true   reason: executor_continuity_not_confirmed
```

у попытки, которая осела **часом раньше**. Формулировка пилота точнее моей:
метрика не молчала, она утверждала, что **ждёт старта, которого никто не
наблюдает и не будет наблюдать никогда**. Поэтому `not_applicable` здесь не
смягчение формулировки, а другое утверждение.

Асимметрия была видна прямо в соседних строках: `executor_time`,
`result_to_acceptance` и `post_execution_settlement` при отсутствии данных
возвращают названную пустоту (`executor_start_not_observed`,
`result_not_received`, `executor_end_not_observed`), и только
`dispatch_latency` шла мимо этого правила.

Теперь различены четыре случая:

| случай | что отдаётся |
|---|---|
| старт наблюдался | измеренный интервал |
| ассистируемая попытка | `not_applicable` / `assisted_dispatch_has_no_process_start` |
| осела, не начавшись | `unavailable` / `executor_start_not_observed` |
| ещё ждёт старта | открытый интервал, как раньше |

Ассистируемая работа вручается, драйвер возвращается на handoff — старта
процесса не наблюдает никто и **никогда**, а не только после оседания. Поэтому
для неё `not_applicable` стоит в любой момент.

## Виды узлов тайминга названы там, где их можно прочитать

В опубликованной схеме `kind` у узла тайминга объявлен просто `string`, без
перечисления. Потребитель не может узнать из контракта, какие узлы бывают, —
и это стоило трёх итераций переписки: я трижды назвал место неверно
(«`from_ref` у метрики `elapsed`», «`intervals` у шага»), а пилот трижды
добросовестно смотрел туда, куда я послал, и находил пусто.

Бандл `foundation` заморожен, перечисление в него не вписать. Оно ушло в
`prifly help`, вместе со вторым фактом, о который мы спотыкались:

```
timing nodes are run, workflow_invocation, stage_activation, step_instance and attempt; there is no "step" node
A node's metrics carry only numbers; the boundaries they were measured between are the same-named entry of its intervals, as from_ref/to_ref
```

Карта узлов измерена пилотом по всем 494 узлам дерева живого захода, а не по
образцу.

## Verification

| Ворота | Где | Результат |
|---|---|---|
| `make check` | локально на `dfc5fe0` + справка | зелёный |
| `make e2e` | локально, то же дерево | зелёный |
| `verify` | GitHub Actions 34298350136 | success |
| `race` | GitHub Actions 34298371227 | success |

**Чужой стенд — и точная граница того, что им подтверждено.** Пилот собрал
кандидат и **перечитал завершённый заход 18 двумя бинарями**, без нового
прогона: правка меняет только чтение, поэтому час машинного времени был не
нужен. Одни и те же данные, разное чтение:

```
0.13.3   9 × quality=unavailable,     reason=executor_continuity_not_confirmed, is_open=true
dfc5fe0  9 × quality=not_applicable,  reason=assisted_dispatch_has_no_process_start, is_open=false
```

**Девять из девяти.** Но подтверждена **одна ветка из четырёх** — ассистируемая:
их заход прошёл чисто, все девять попыток ассистируемые и все осели. Ветки
«старт наблюдался», «осела не начавшись» и «ещё ждёт старта» стоят только на
локальном тесте `TestDispatchLatencySaysWhyItIsEmpty`, проверенном
отрицательно (со старым кодом краснеет). Записано так по прямой просьбе пилота,
и он прав: иначе вышло бы утверждение шире собранного доказательства.

Пакетчик эту правку подтвердить не может по построению: их прогоны стоят на
handoff, ассистируемых попыток с оседанием у них в этой форме нет.
