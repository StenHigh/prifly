# Выпуск Pri-Fly 0.13.24

Решение владельца по карте «есть / нет / чем заменить» (2026-09-12): «делай все
по порядку». Четыре места объявления, ни одного нового механизма доверия,
ни одного изменения формата Run'а. Цель владельца — меньше обвязки и
управляющих текстов для ИИ у проекта; движок остаётся универсальным.

## 1. Программа для вставного шага — в `extend.yaml`

Было: привязки исполнения читались только из корневого `workflow.yaml` пакета
(`project_execution.go`), поэтому вставной шаг проекта мог быть только
ассистируемым — его программа тестов требовала сессии ИИ.

Стало: `execution_bindings.steps.<short name>` в `extend.yaml`, ключ — имя
шага, который вставляет одно из расширений этого файла; форма, `project local
set --allow-executable`, `--allow-execution` и worker protocol — те же, что у
пакетной привязки. Привязка для шага, который ни одно расширение не вставляет,
и шаг, привязанный и пакетом, и проектом — отказ: программа пакета не
переопределяется. Разрез: без слияния — `execution-bindings.json` не
запечатывается.

## 2. Поддерево `project/` в папке пакета

Было: файлы проекта в папке пакета (вставные `steps/*.yaml`) считались
правкой upstream — `workflows update` отказывал `project_workflow_modified`, и
команда шла через remove → add → восстановить (`build-package.sh` пилота);
компилятор читал компоненты только из подпапок пакета.

Стало: `<папка пакета>/project/{steps,contexts,schemas,checks,workflows}` —
команды, как `extend.yaml`: исключено из drift-digest'а, переносится при
`update` байт-в-байт, читается компилятором; upstream с папкой `project/` —
отказ. Разрезы: компилятор без `project/` — ровно `project_extension_unknown_step:
tests (known: build, commit)` пилота; update без переноса — файл исчезает.

## 3. Постоянный `workspace` у launch

`launches.<id>.workspace: worktree|checkout` в `project.yaml`. Применяется
там, где workflow требует рабочую копию; где `--workspace` был бы отказан как
лишний (`project_start_workspace_unused`), постоянный выбор молча не
применяется — это ответ на вопрос, а не флаг. Анкета называет его в
`workspace`; текст раннера велит использовать без вопроса (новый digest, текст
0.13.21–0.13.23 заморожен вариантом 10); `--workspace` перебивает на один Run,
файл не переписывается.

## 4. Предстартовая программа `preflight`

`launches.<id>.preflight: {executable, args, timeout_ms}`. Бинарь — из
`local.yaml` (`--allow-executable`), `--allow-execution` не нужен: это
собственное объявление проекта, не программа пакета. Исполняется в корне
repository с окружением оператора до компиляции и любого захвата (пакет не
импортирован, claim не взят, Run не создан). Ненулевой код —
`project_start_preflight_failed: launch X preflight shell exited 3; nothing was
started; output: <хвост>`; таймаут — `project_start_preflight_timeout`.
`--prepare` остаётся read-only и программу не исполняет. Разрез: без вызова
start проходит мимо несуществующего бинаря.

## Что это закрывает у пилота

Лаунчер и `PROJECT.md` уходят почти целиком: `workspace` и пять ответов — в
дереве (0.13.23 + 3), проверка базы — `preflight` (4), `tests` — шаг-программа
с выходом по схеме порта (1) в `project/` (2), `build-package.sh` не нужен.
Наружное действие после `commit` — тем же путём (1): вставной шаг-программа
`git push` + `glab mr create --draft` с выходом `{branch, mr_url}`.

Авторские схемы `extension-v1` и `project-profile-v3` получили необязательные
поля (аддитивно, версии те же); справочники показывают блоки.

## Ворота

`make check` (race), `make e2e`, CI `verify`; каждая из четырёх частей
вырезана и показала свой старый ответ.
