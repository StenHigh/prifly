## Context

Мотивация — proposal.md, раздел Why. Состояние кода 0.13.67:

- Объявленный эффект шага есть только в `Run.Definitions[].Bytes`, а `View`
  вырезает их до ответа. Поэтому эффекты вычисляются до вырезания и идут
  рядом с RunView полем `json:"-"`: текстовая сводка их печатает, JSON
  RunView не меняется, а JSON несёт их в `core-next/42`. Текстовый
  `run status` печатает шаги строками `step "…" status=… verdict=… outputs=…`
  (`cmd/prifly/main.go` около 2233), `run explain` — маршрут без эффектов.
- `project start` в нейтральном пути пишет сводку в stderr
  (`cmd/prifly/project_start.go` около 487) до открытия engine. Бюджет Registry
  считается функцией `projectRegistryBudgetAfter`, которую уже вызывает
  `--prepare`, а на пути старта предел срабатывает позже, при установке пакета.
- Действие `run next` вычисляет `nextKind` (`internal/runtime/engine.go`
  около 560–612); задание, ждущее хоста, даёт `idle`. Версия ответа берётся из
  `versionContracts[...].Next` (`internal/runtime/versions.go`). Прецедент
  «ответ-версия без новой строки состояния» — 36 и 41: состояния, которые ещё
  создаются, переходят на новую версию ответа.
- `run events` отдаёт `foundation-events/1` с `view.events` и `next_after`
  (`cmd/prifly/main.go` около 1025).
- Каталог монитора уже умеет перечислять Runs authority (`MonitorRevisions`,
  `MonitorSummary`).

## Goals / Non-Goals

**Goals:**
- Каждое из шести мест проходится по справке и ответам команд без знания
  внутренностей. Проверка — холодный заход слабой модели (задача 7).
- Ни одна опубликованная версия контракта не меняется.

**Non-Goals:**
- Смена формы `foundation-events/1` или прежних версий `run next`/`run status`.
- Общая очистка истории Runs (это монитор) или бюджета Registry сверх change
  `auto-retire-unused-package-editions`.
- Живое прерывание внешней записи (задача 6.3 соседнего change).

## Decisions

**1. Эффект шага — вычисляемое чтение, а не новое поле состояния.** Читается
из запечатанного определения шага при построении ответа. Состояние Run не
меняется, новой версии состояния не нужно. Текстовый вывод меняется свободно.
JSON получает эффекты в `core-next/42`, общем ответе `run next` и
`run explain`: `step_effects` для каждого экземпляра шага и `effects` у стадии
текущего действия. Версия RunView закреплена состоянием Run. Новая версия
чтения без новой строки состояния прецедента не имеет, а next-ответ имеет (36,
41), поэтому RunView не трогаем. Отвергнуто:
писать эффект в событие Attempt — это новое состояние ради того, что уже
запечатано.

**2. Сводка печатается после всех отказывающих проверок.** Бюджет Registry,
стабильность ревью и прочие предусловия считаются до вывода сводки, тем же
кодом, что `--prepare`. Отвергнуто: отложить печать сводки до создания Run.
Сводка нужна хосту до исполнения, её смысл — показать, что будет запущено.

**3. `awaiting_host` в `core-next/42`.** Новое значение действия требует
новой версии ответа. Её берут состояния, которые ещё создаются, как 36 и 41.
Новая строка состояния не нужна. Прежние Runs отвечают по своей версии.
`safe_next_actions` сохраняет `session.task`: читатели пары полей не ломаются.
Отвергнуто: оставить `idle` и лечить только документацией. Пилот описан в
troubleshooting и всё равно застрял; слабая модель читает `action`.

**4. `run list` поверх каталога монитора.** Команда использует те же чтения
(`MonitorRevisions`/`MonitorSummary`), что и монитор. Второй способ
перечислять Runs не появляется. Формат `run-list/1`. Отказ на неизвестную
операцию `run` включает `list` в список допустимых.

**5. `package restore` называется в тексте, механизм не меняется.** Вывод уже
обратим. Не хватало только слов, по которым хост или владелец это видят.

**6. `auto-retire-unused-package-editions` исполняется по своим артефактам.**
Этот change ссылается на него задачей и не копирует его требования. Архивация
— отдельно, по готовности.

## Risks / Trade-offs

- [Потребители `run next` ждут только известные действия] → Мосты пакета и
  skill `prifly-run` предупреждаются до выпуска. Новое действие приходит только
  от Runs, созданных сборкой с `core-next/42`. Проверка пакета — его ворота на
  выпуске.
- [Сводка позже на время проверки бюджета] → Тот же расчёт уже делает
  `--prepare`, он дешёвый.
- [`run list` на большой authority] → Постранично, как чтения монитора.
- [Холодный заход слабой модели недетерминирован] → Задание и найденные
  застревания записываются в tasks.md вместе с командой и моделью. Каждое
  застревание — либо исправление, либо запись, почему это не дефект.

## Migration Plan

Совместимо назад: новые версии ответов публикуются рядом с прежними, прежние
Runs отвечают по своим. Порядок выпуска: предупредить сессию пакета о
`awaiting_host` и новых полях → тег → ворота пакета. Откат: предыдущая сборка
отвечает для тех же Runs по `core-next/41`, потому что состояние Run не
меняется.
