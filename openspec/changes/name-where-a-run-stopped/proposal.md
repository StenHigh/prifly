## Why

Заход #152 завершился с `outcome: rejected`, и ни один ответ authority не
сказал, **где** граф свернул к этому исходу. Хост восстанавливал это руками:
прочитал `activations`, нашёл в главной invocation finish-стадию `abandoned`,
а потом открыл исходник workflow (`extend.yaml`), чтобы понять, какое ребро
туда привело. Оба факта у authority есть: finish-активация записана в
состоянии, ребро объявлено в запечатанном плане, который Run несёт с собой.
Читатель пошёл в graph руками ровно потому, что ответ их не назвал — это тот
же класс, что курсор `run events`: authority держит факт и не говорит его.

## What Changes

- Ответ о следующем действии для терминального Run называет место остановки:
  invocation, finish-стадию, её исход и — когда он однозначно выводится из
  запечатанного плана — стадию и вердикт ребра, которое к ней привело.
- Ребро выводится вызовом той же функции маршрутизации, которой шёл драйвер,
  а не вторым описанием правил. Неоднозначность (к этой finish ведёт больше
  одного объявленного ребра из исполненных стадий) MUST читаться как
  отсутствие, а не как выбор одного из вариантов.
- Минтится только `core-next/36`: ответ ничего не записывает, состояние Run
  не меняется. Поэтому новый ответ доступен и уже существующим Run — тем, чьи
  state-версии сегодня отвечают под `core-next/33`, `/34`, `/35`.
- Документируется в `examples/troubleshooting.md` рядом с остальными
  вопросами «откуда это взять, не открывая хранилище».

## Capabilities

### Modified Capabilities

- `cli-protocol`: ответ о следующем действии для терминального Run называет
  место остановки и объявленное ребро, которым оно достигнуто.

## Impact

- `internal/runtime/engine.go`: `NextView`, ветка `terminal` в `Next`.
- `internal/runtime/model.go`, `versions.go`, `compatibility.go`: константы
  `core-next/36`, строки лестницы, объявленная capability.
- `cmd/schema-gen/`: бандл `core-run-finish:36`.
- `schemas/`: новый опубликованный бандл; прежние не меняются.
- `examples/troubleshooting.md`.
