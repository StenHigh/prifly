# Проверять migration при action admission и до legacy Project effects

**Date:** 2026-11-09
**Files:** internal/runtime/actions.go, internal/runtime/package_lifecycle.go, cmd/prifly/project_start.go
**Severity:** high

## Проблема

После повторного revoke или quarantine supplier открытая assisted session ещё
допускала новый action. Legacy Project `/2` принимал migration-флаг без
reviewed summary и мог возвращать некорректный `project-start/9`.

## Причина

Интеграция проверяла executor и nested admissions, но отдельный action admission
проверял только tool. Структурный Run invariant не проверяет текущие lifecycle
facts. Выбор новой версии Project-ответа проверял flag, а построение summary
проверяло независимый selector `neutral`; сочетание `/2` с flag не было покрыто.

## Решение

Action admission проверяет Run binding и tool по одному package snapshot.
Один CAS pin связывает проверку с атомарным admission и потреблением approval.
Tool сохраняет обычный gate без schema exception. Legacy Project отказывает
при выборе migration до import, claim или Run. Обычный legacy Start сохранён.

До исправления реальные migration Runs допускали action после invalidation.
Legacy regression доходила до создания и rollback claim вместо раннего отказа.
После исправления те же regressions проходят. Отказ сохраняет Run version,
пустые action ledgers и approved approval. CLI refusal сохраняет authority cut
и claims. Диагностика использует существующие Problem/receipt границы; tests
пишут `[FIX:21]` input/outcome, runtime не получает новый debug stream.

## Предотвращение

- При новом admission binding найти все public admission entry points.
- Проверить переходы внутри открытой сессии после lifecycle mutation.
- Покрыть сочетание каждого profile selector с новым opt-in flag.
- Сначала проверить применимость flag, затем создавать authority effects.
- Не заменять lifecycle validation структурной проверкой сохранённого JSON.
