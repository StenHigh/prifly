# Немедленная инвалидация ответов при смене фильтра

**Дата:** 2026-10-15 18:54 UTC
**Файлы:** cmd/prifly/monitor.js, test/e2e/verify-monitor-board.cjs
**Серьёзность:** medium

## Проблема

Прежний пустой ответ HTTP очищал доску под уже выбранным новым фильтром.
Проверка только конечной карточки пропускала кратковременную неверную установку.

## Причина

Идентичность запроса (generation) обновлялась в отложенном callback через
200 мс вместе с отправкой следующего запроса. DOM фильтра менялся немедленно,
а прежнее поколение оставалось допустимым в течение debounce.

## Решение

На input немедленно увеличить generation, сбросить страницу и раскрытие поиска.
В таймере оставить только schedule. Прежний tick завершает busy/queued обычным
путём, а его ответ уже не может изменить DOM.

Регрессия получает настоящий HTTP ответ через route.fetch, задерживает его,
замораживает browser clock, меняет фильтр и отпускает ответ до debounce.
MutationObserver читает каждый добавленный grid, включая уже удалённый:
проверка падает до исправления и проходит после него. Debug diagnostic
`[FIX:monitor-filter]` живёт только в Node harness при LOG_LEVEL=debug.

## Предотвращение

Инвалидировать асинхронные результаты синхронно с изменением пользовательского
выбора. Debounce откладывает работу, а не смену идентичности. Для таких гонок
проверять промежуточные установки DOM с контролируемым временем и реальными
HTTP данными, а не только конечное состояние после задержки.
