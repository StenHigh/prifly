## Context

Причина изменения изложена в [proposal.md](proposal.md). Проверенный исходный commit: `2060fc9286cff2924e198b0294ba9a2814ad0e90`.

Сейчас `prifly-run` содержит большой общий протокол и частные процедуры восстановления.
Канонический текст формируется в `cmd/prifly/project.go`; копии в host roots сами по себе не являются источником шаблона.
`project runners update` узнаёт прежние тексты по точным bytes и сохраняет `PROJECT.md`.
`project_runner_upgrade_test.go` закрепляет digest текущих и исторических вариантов.
Изменение шаблона без замораживания прежнего текста ломает обновление уже установленных runners.

Существующие справочники покрывают авторинг по полям и часть эксплуатационных симптомов.
Общего индекса операций и доставляемого локального руководства сейчас нет.
Правила проекта запрещают новую `docs/`-wiki; подробности размещаем в `examples/`.
`aif-docs` здесь не применяется: [его overlay](../../../.ai-factory/skill-context/aif-docs/SKILL.md) прямо запрещает этот workflow.

Проверенные реализации обновления:

| Часть | Существующий интерфейс | Ограничение |
|---|---|---|
| Binary | `update --json` | Проверяет signed stable и сразу заменяет managed binary при новой версии; отдельного `--check` нет |
| Workflow | `project workflows update NAME --repository DIR --json` | Проверяет настроенный ref; сохраняет `extend.yaml` и `project/`; отказывает при drift upstream-owned files |
| Runner | `project runners update --check --repository DIR --json` | Read-only сравнение известных generated templates; чужой текст вызывает конфликт |
| Runner | `project runners update --repository DIR --json` | Применяет обновления известных templates; не добавляет отсутствующий host автоматически |

Сеть используется только через явные операции; прямой `project start` не проверяет обновления скрыто.
Source build и copied binary не поддерживают self-update.
`project workflows` перечисляет launches, поэтому его результат нельзя использовать как список всех имён установленных packages.
Для обхода установленных packages нужны declared `packages` и `origin` из project profile.

## Goals / Non-Goals

**Goals:**

Дать агенту полный маршрут от намерения до команды, результата и следующего действия.
Доставить этот маршрут в сторонний проект без зависимости от checkout Core.
Снизить объём чтения во время обычного Run и измерить результат на одинаковых задачах.
Обновлять установленные компоненты до нового запуска с сохранением настроек и проверок доверия.

**Non-Goals:**

Не менять authority runtime, YAML semantics, опубликованные JSON-поля или закреплённые Runs.
Не писать новую нормативную спецификацию внутри руководства.
Не устанавливать workflows или hosts, которых пользователь не выбрал.
Не обещать конечный список всех комбинаций произвольных inputs, shell arguments и внешних систем.
Не обновлять окружение внутри уже выданного Attempt и не выполнять release от имени владельца.

## Decisions

### 1. Полнота означает покрытие проверяемой публичной поверхности

Карта [coverage.md](coverage.md) распределяет команды, capabilities и варианты по страницам.
На реализации карта сверяется с dispatch/help/schema текущего исходного снимка, а не только с этим предварительным перечнем.
Для команды перечисляются все поддержанные flags, defaults, взаимоисключения и версии.
Сочетания показываются как независимые измерения; важные взаимодействия имеют отдельные сценарии.
Неподдержанная комбинация получает точный отказ или явное ограничение.

Слова «всё описано» допустимы после сверки, но не доказывают отсутствие неизвестного дефекта.
Наличие строки в индексе не заменяет проверку процедуры.

### 2. Один короткий skill и тематические страницы

Предлагаемое дерево поставляемых материалов:

```text
prifly-run/
|-- SKILL.md                  обязательный протокол и маршрутизация
|-- PROJECT.md                правила проекта; пользователь владеет файлом
`-- references/
    `-- manual/
        |-- index.md          задача / симптом / команда -> страница
        |-- installation.md   binary, workflows, runner, обновления
        |-- launch.md         выбор, questionnaire, prepare, start
        |-- hosting.md        next, task, take, drive, output, submit
        |-- decisions.md      preflight/runtime и native questions
        |-- recovery.md       continue, resume, reopen, recover, resolve
        |-- workspace.md      claims, effects, worktree, checkout
        |-- authoring.md      поля, schemas, примеры и composition
        |-- artifacts.md      refs, sources, task, packages, trust
        |-- control.md        stops, approvals, grants, receipts
        |-- observability.md  monitor, Light, events, timing, telemetry
        |-- operations.md     queue, capacity, storage, cleanup
        `-- troubleshooting.md симптомы и решения
```

Канонические страницы находятся в `examples/operations/`.
Один Go `embed.FS` рядом со страницами включает их в CLI build; CLI доставляет exact bytes в host roots.
Пакет с embedded страницами не импортируется authority runtime и не содержит предметной логики.
Это стандартная доставка assets; custom document builder или HTML generator не создаётся.

Существующие `examples/authoring/` остаются каноническими справочниками полей.
В доставку включаются нужные reference YAML/Markdown и их локальные зависимости на примеры и schemas.
Общий embed boundary для `examples/` может находиться в `examples/embed.go`; он включает только явно выбранные assets.
Схемы, уже доступные через `prifly schema`, запрашиваются по точному имени вместо ненужного копирования всего schema tree.
Если пример имеет относительную ссылку, доставка либо включает её цель, либо явно даёт команду `schema` для installed версии.
Список assets и локальные ссылки проверяются в установленной временной структуре, где Core checkout отсутствует.

Все внутренние ссылки manual остаются относительными и работают в репозитории и установленной копии.
Ссылки на нормативные источники при доставке ведут на соответствующий release tag, а не на moving `main`.
Для dev build указывается source commit и статус unreleased; он не объявляется stable release.
Идентичность поставки и digest assets хранятся в служебном metadata установки runner.
Этот metadata не является новым runtime contract или trusted package.

Альтернатива — только URL на wiki — требует сети и может показывать возможности другой версии.
Альтернатива — один огромный skill — заставляет читать нерелевантные разделы на каждом запуске.
Выбранная доставка даёт локальные страницы нужной версии и чтение по требованию.

### 3. Страница операции имеет конкретный ответ

Каждая процедура содержит:

1. Задачу пользователя, условия применения и минимальную поддержку.
2. Рабочий каталог, источник executable и нужный authority root.
3. Точные команды с объяснёнными placeholders и реальными источниками ID/digest.
4. Поддержанные flags, defaults, варианты входов и правила совместимости.
5. Значимые поля JSON, успешный результат и состояния ожидания.
6. Допустимые эффекты, подтверждения и границы полномочий.
7. Частые отказы, безопасное следующее действие и условия остановки.
8. Проверяемый пример и ссылку на канонический источник.

Примеры не копируют случайные runtime IDs и не предлагают извлечение внутренних refs из БД.
Большие ответы сокращаются до нужных полей с явной пометкой о сокращении.
Инструкции пишутся по-русски короткими предложениями; имена контрактов и команд сохраняются.

### 4. Обязательный preflight выполняется до выбора и prepare

Preflight здесь означает проверку установки перед запуском; это не новый workflow stage или package preflight program.
Порядок действий runner:

```text
новый start / continue / recover
             |
             v
local config -> binary update -> version/capabilities
                                      |
                                      v
                      installed workflows update
                                      |
                                      v
                       runner + manual check/update
                                      |
                                      v
                  перечитать skill/PROJECT.md/launches
                                      |
                                      v
                  questionnaire -> prepare -> review -> start

ошибка проверки/обновления -> точная причина -> нового Run нет
существующий Attempt      -> pinned task -> обычный host protocol
```

Используется точный `prifly_executable`, затем тот же путь после atomic replacement.
Runner записывает версии до и после, updater source, workflow ref/commit и применённые изменения.
Полный JSON не загружается в разговор, если достаточно этих полей.
Updater не вызывается через самодельный URL или скачанный shell installer.

Обновляются все уже объявленные upstream packages, включая dependencies, а не только package выбранного launch.
Это позволяет делать окончательный выбор по актуальному списку.
Авторские локальные packages перечисляются отдельно: у них нет обещания удалённой актуальности.
Новый package автоматически не устанавливается.
Workflow update сохраняет upstream ref и не получает `--ref` без явного решения владельца.

Для catalog-installed package runner проверяет соответствующую запись исходного каталога через публичный `search`.
Если запись теперь указывает новый release ref/commit, runner показывает переход и получает выбор владельца до смены ref.
Для прямого Git origin проверка относится к записанному ref.
Фиксированный tag/commit не является подпиской на будущие releases: runner явно сообщает эту границу.
Переход на другую линию выпуска не угадывается по имени последнего Git tag.

После обновления повторно читаются skill и `PROJECT.md`.
Если новый skill тоже требует preflight, текущая успешная проверка той же подготовки не запускает рекурсию.
Повторный независимый запуск требует новой проверки; постоянный TTL-cache не ослабляет требование пользователя.
Проверка не создаёт Run, claim, imported/trusted package и не исполняет программы workflow.
Предварительная загрузка source bytes не означает доверие или admission.

У пользователя уже есть намерение обновляться перед запуском.
Повторное согласие на обычную разрешённую процедуру не добавляется.
Host execution permissions и подтверждение итогового summary остаются отдельными границами.
Source build, отсутствие receipt, недоступная сеть или конфликт завершают подготовку диагностикой.
Автоматического обхода через продолжение на старой версии нет.

При active Run его просмотр, drive и выполнение текущего Attempt не требуют новой установки.
`run reopen` работает с прежним Run; это правило не превращает его в запуск на новом package.
Review для `continue` и `recover` строится после обновления, чтобы проверять фактическую совместимость source evidence с новой сборкой.

### 5. Обновление справочника соблюдает владение файлами

Установка runner доставляет skill, manual и metadata поставки одной согласованной группой.
Проверка предварительно сравнивает все управляемые файлы, прежде чем перезаписывать хотя бы один конфликтующий файл.
Известные прежние assets узнаются по digest; изменённый пользователем asset вызывает отказ.
Недостающая страница восстанавливается явным update; пользовательские файлы остаются.
Новый код не рекурсивно очищает весь `references/` и не считает чужие файлы управляемыми.
Сбой записи не должен оставлять новый skill со старым несовместимым manual без явной диагностики.

Замораживаются прежний шаблон и его recognition chain до изменения текущего шаблона.
Проверяются все три host variants и каждый уже известный historical runner.
Меняются канонический шаблон и tracked host copies, а не только копии в этом репозитории.
Missing host остаётся missing; `update` не подменяет явный `runners add`.

### 6. Полнота и экономия проверяются разными способами

Автоматическая проверка покрытия сопоставляет CLI registry/help, flags и capabilities с индексом.
Она не использует один вручную скопированный список как обе стороны сравнения.
Для declared capabilities сохраняется существующий `TestEveryDeclaredCapabilityIsInTheAuthorIndex`.
Новая проверка дополняет его эксплуатационными процедурами, не заменяя authoring index.
Проверка ссылок работает в обеих структурах: canonical examples и установленный runner.

Практические проверки выполняются в fixture-проекте с установленным CLI и manual, без исходников Core.
Случаи описаны в coverage; результаты проверяются по authority/CLI, а не по наличию слов в skill.
Один случай намеренно скрывает нужную страницу: агент должен сообщить пробел или использовать публичный CLI.
Отсутствие прямого ответа не должно запускать бесконечный поиск.

Для оценки экономии один и тот же набор задач выполняется со старым и новым skill.
Фиксируются model/host settings, прочитанные bytes, tool calls, source reads и результат операции.
Фактические tokens/cost записываются только при доступном измерении хоста.
Без такого измерения отчёт использует bytes и calls, а token savings остаются неизвестными.
Успех требует правильного результата без чтения Core, а не только меньшего объёма текста.

## Risks / Trade-offs

- Обязательная сеть мешает offline старту → остановка с причиной; просмотр и исполнение существующего Run остаются доступны.
- Обновление binary меняет общий executable → показать exact path и версии; не заменять запущенный driver своим процессом.
- Новый package несовместим с local settings → сохранить настройки и показать diagnostic до Run; не «чинить» YAML молча.
- Preflight меняет tracked files → показать изменённые пути; не добавлять скрытый commit и проверить поведение dirty repo/worktree.
- Несколько запусков обновляют одни assets → проверить concurrent update и не объявлять успех при смешанной поставке.
- Полный справочник увеличивает binary → включать текстовые assets явно; измерить размер до и после.
- Пустая строка coverage создаёт ложную полноту → проверять команды в fixture и читать примеры на ревью.
- Main docs опережают stable → локальная поставка, release-tag links и обязательная проверка capabilities.
- Нельзя перечислить произвольные combinations → покрывать каждый option и проверенные взаимодействия с явными границами.

## Migration Plan

1. После подтверждения change выполнить задачи [tasks.md](tasks.md) через объявленный проектный workflow.
2. Сначала зафиксировать baseline покрытия и неизменность прежних runner templates.
3. Создать страницы, доставку assets, обновление runner и preflight-инструкции.
4. Проверить обновление старых installations, настройки проекта и практические сценарии.
5. Выпустить обычным owner-controlled release process; документационный gate не означает release qualification.
6. При проблеме остановить новые запуски и сохранить диагностические данные; не понижать storage или переписывать прежние Runs.

Возврат текстовых изменений в исходниках выполняется обычным новым commit владельца.
Для установленного binary не предлагается несуществующий downgrade flag.
Исторические templates и evidence не переписываются при исправлении.
