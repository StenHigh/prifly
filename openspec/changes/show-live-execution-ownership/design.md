## Context

См. `proposal.md`. Монитор уже читает закреплённый Run, дерево invocation/activation/attempt и периодически обновляет выбранный read cut. Он не имеет канала к внешнему агенту и не должен превращать выдачу задания в утверждение о том, что процесс жив.

## Goals / Non-Goals

**Goals:**

- Свести записанные lifecycle-факты в короткую навигационную панель «сейчас».
- Объяснить роль узла одними и теми же данными в схеме, дереве и карточке.
- Сохранить distinction между call-вложением, host-сессией, локальной программой и provenance fork.

**Non-Goals:**

- Pause/cancel/retry, перепривязка host или иные команды управления.
- Проверка живости внешнего процесса, чат-статусы, tool calls и вывод программы, если они не записаны в Run.
- Новая durable модель или миграция исторических Run.

## Decisions

### Собрать read-only snapshot из уже записанного Run

Классификация — одна функция монитора `executionRole`, а activity rows — `activityRows`; обе чистые, в `cmd/prifly/monitor.js`, и читают тот же read cut, что `/api/run` уже отдаёт целиком. Карточка узла и сводка «Сейчас» вызывают одну и ту же функцию, поэтому классификации не расходятся. Место Run в очереди допуска — факт authority, а не Run: сводка берёт его из уже существующего `/api/capacity`, который монитор читает для живого Run.

Первоначально проекцию предполагалось собрать в Go. При реализации UI-части (2.1, 2.2) классификация уже оказалась одной клиентской функцией, а API и так отдаёт полный Run атомарно с его версией; вторая, серверная копия той же классификации создала бы именно два источника, от которых эта альтернатива должна была защитить. Проверка — `node cmd/prifly/monitor_ui_test.cjs`, а read-only характер API не меняется: новых маршрутов и полей нет.

### Роль выводится только из типизированных фактов

`session` означает выданную внешнему host Attempt; `process` — локальную программу; workflow stage kind определяет управляющий или вложенный узел. «Субагент» выводится лишь при записанном явном идентификаторе/типе, иначе интерфейс показывает executor/host как записан. Fork берётся исключительно из `Run.Fork` и никогда из call, branch или session.

Альтернатива — угадывать роль по имени executor или workflow. Она создаёт ложную ownership-информацию и отвергнута.

### Состояние формулируется как факт read cut

Для active Attempt показывается «исполнение начато», когда это записано. Для session без такого факта — «выдано, ожидается отчёт». Ready, decision и wait показываются как причины ожидания только при наличии соответствующего поля. Summary получает read-cut вместе с Run, поэтому polling обновляет его атомарно с деталями.

## Risks / Trade-offs

- [Старые Run не содержат достаточной identity/роли] → явная метка «не записано», без fallback-эвристик.
- [Несколько причин ожидания одновременно] → показывать отдельные строки, не выбирать одну «главную» без записанного правила.
- [Большой Run перегружает summary] → ограничить сводку текущими активными/ready/waiting объектами; полный список остаётся в дереве.

## Migration Plan

Изменение добавляет только локальную read-проекцию. Старые Run не переписываются: после обновления monitor показывает их сохранённые факты либо явную неполноту. Откат к прежнему binary безопасен, поскольку durable state и внешние контракты не меняются.
