## Why

Пилот провёл Run #174 (`run:d8e2863…`, aif-classic, Pri-Fly 0.13.66) до
`succeeded`. Шесть мест он прошёл только потому, что сильная модель
догадалась, где искать ответ. Более слабая модель или человек без знания
внутренностей там остановились бы. Цель владельца — инструмент, с которым
одинаково просто работать человеку и слабой модели. Поэтому каждая находка
Run считается дефектом, даже если её удалось обойти. Решение владельца от
2026-09-29.

Находки, проверенные по коду 0.13.67:

1. **Объявленный эффект шага не виден при чтении Run.** Класс эффекта,
   `retry_class` и граница `external_write` запечатаны в определениях Run, но
   `View` вырезает определения из каждого ответа чтения
   (`internal/runtime/engine.go`, «Views never dump … raw definitions»). В
   `run status` (текст и JSON), в `run explain` и в событиях их нет. Пилот искал
   границу и не нашёл. Анонс 0.13.66 («журнал Run несёт границу») обещал
   больше, чем показывает чтение. Первая версия этого proposal тоже ошибалась,
   утверждая, что граница видна в `.run.definitions[].bytes`: при реализации
   выяснилось, что этого поля в ответе нет.
2. **Отказ идёт после документа, похожего на успех.** `project start` пишет
   предстартовую сводку `project-launch-summary/3` в stderr и только потом
   проверяет бюджет Registry. Отказ `dependency_limit` приходит вторым JSON в
   тот же поток, stdout пуст, код возврата 2. Читатель, который берёт первый
   объект из объединённого вывода, видит сводку и считает запуск успешным.
3. **`run next` сразу после старта отвечает `action: idle`.** Задание в этот
   момент уже выдано и ждёт хоста. `session.task` стоит в
   `safe_next_actions`, в troubleshooting описано, что читать нужно пару
   полей. Но модель, которая смотрит только на `action`, решает, что делать
   нечего.
4. **Нет способа увидеть Runs authority из CLI.** `run list` отвечает
   `"list" is not a run operation`. Id Run пилот достал из
   `capacity show` → `held`.
5. **`run events --json` кладёт события в `.view.events`.** Форма закреплена
   опубликованным контрактом `foundation-events/1`, и её не меняем. Первая
   выборка пилота по `.events` вернула ноль событий, и ни справка, ни ответ не
   подсказали путь.
6. **`dependency_limit` набегает от старых редакций пакета.** 524 записи при
   пределе 512: четыре редакции `aif:package/classic` держат 232 из них.
   Снять их можно только вручную, через `package remove`. Хост отказался
   выполнить это без владельца: счёл удаление необратимым, хотя `package
   restore` его отменяет, и отказ этого не говорит. План автоматического
   вывода старых редакций уже есть в change
   `auto-retire-unused-package-editions` (0/8), но он не реализован.

Задача 6.3 change `let-a-program-step-declare-an-external-write` (живое
прерывание программы с внешней записью) остаётся в своём change до Run, в
котором прерывание случится.

## What Changes

- **Эффект шага виден там, где читают Run.** `run status` (текст) и
  `run explain` называют для каждой шаговой стадии класс эффекта и
  `retry_class`, а для `external_write` ещё и границу: систему, операции и
  цель. JSON-чтения получают то же в новой версии ответа, рядом с прежней.
  Прежние опубликованные версии не меняются.
- **Всё, что может отказать, проверяется до сводки.** `project start`
  проверяет бюджет Registry и остальные предусловия до того, как пишет
  предстартовую сводку. Отказ приходит единственным документом. Если после
  сводки всё же приходит отказ, первой строкой в stderr идёт не сводка.
  Справка говорит, какой поток что несёт.
- **`run next` называет ожидание хоста своим действием.** Новая версия ответа
  `run next` добавляет действие `awaiting_host` для случая, когда драйверу
  делать нечего, а выданное задание ждёт хоста. `idle` остаётся только для
  состояния, в котором не ждёт никто. Ответ несёт `next_command` —
  `session task --run RUN --all`, а инструкция раннера `prifly-run` говорит,
  что с ним делать.
- **`run list`.** Новая команда только для чтения показывает Runs authority,
  новые первыми: id, workflow, статус, исход, время создания и отметку, ждёт
  ли Run хоста. Формат `--json` версионирован.
- **Путь к событиям назван.** Справка `run events` показывает, что события
  лежат в `.view.events`, а продолжение — в `next_after`. Текстовый вывод
  `run events` печатает сами события, а не только их число.
- **Старые редакции пакета выводятся автоматически.** Реализуется change
  `auto-retire-unused-package-editions` целиком, по его спецификации и
  задачам. Здесь к нему добавляется одно: отказ `dependency_limit` и справка
  `package remove` говорят, что вывод обратим через `package restore`, и
  приводят готовую команду.
- **Проверка слабой моделью.** Холодный заход модели уровня Haiku проходит по
  этим шести местам только с помощью справки и ответов команд. Где заход
  застрял — это дефект этого change.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `cli-protocol`: `run list`; порядок проверок и вывода `project start`;
  действие `awaiting_host` в `run next`; эффект шага в `run status` и
  `run explain`; справка по `run events` и `package remove`.
- `domain-execution`: объявленный эффект шага — читаемый факт Run, а не только
  запечатанные байты.

Автоматический вывод старых редакций пакета описывают дельты change
`auto-retire-unused-package-editions` (`workflow-and-context`,
`runtime-resources`, `cli-protocol`). Этот change их не дублирует.

## Impact

Изменение затрагивает runtime продукта. Владение нормативными источниками не
меняется.

- Код: `internal/runtime` (next-ответ, чтение эффекта шага, run list),
  `cmd/prifly` (`project_start.go`, `main.go`: справка, `run list`,
  `run events`, текстовые выводы), плюс код change
  `auto-retire-unused-package-editions`.
- Опубликованные контракты: новая версия next-ответа (`core-next/42`) и новая
  версия JSON для `run status`/`run explain` с эффектом шага. Обе публикуются
  рядом с прежними, закреплённые бандлы не меняются. Новый формат `run-list/1`.
- Потребители: мосты пакета и skill `prifly-run` читают `action` из `run next`.
  Сессию пакета нужно предупредить до выпуска: новое действие
  `awaiting_host` приходит от Runs в тех состояниях, которые перейдут на
  `core-next/42`.
- Документация: `examples/troubleshooting.md` (записи про `idle` и
  `dependency_limit`), справочник шага (как увидеть объявленный эффект),
  `examples/README.md` (новые возможности).
