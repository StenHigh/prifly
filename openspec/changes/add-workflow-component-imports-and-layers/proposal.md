## Why

Pri-Fly уже поставляет отдельные workflows, но проект не может переиспользовать их компоненты без копирования исходников. Расширения classic и profiled в smsplace повторяют общие настройки, тесты и публикацию Draft MR.

Нужен читаемый способ собрать свой workflow из базового маршрута, производных workflows и компонентов других пакетов. Несколько производных должны объединять дополнения, а общий classic — выполняться один раз. Основной пример — обязательная оценка применимости UI/UX вместе с другими проверками после тестирования.

## What Changes

- Добавить явные публичные экспорты workflow и step из Project workflow folder. Supporting schemas, contexts, checks и программы входят через зависимости экспорта.
- Добавить импорт экспортов из пакетов, явно объявленных в `project.yaml`. Compile не скачивает зависимости и не выбирает последнюю установленную версию.
- Добавить наследование от одного или нескольких производных workflows с общей закреплённой базой. Общие предки и унаследованные дополнения включаются один раз.
- Позволить производному workflow добавлять шаг или структурированную развилку без копирования classic. При объединении автор явно выбирает sequence, parallel или choice для пересекающихся дополнений.
- Добавить упорядоченные локальные слои `extend.yaml`. Каждый слой использует ограниченные настройки и вставки, а не произвольное слияние YAML.
- Показать итоговую последовательность, происхождение настроек и границы импортов до запуска. Автор читает короткую конфигурацию; подробности открывает по запросу.
- Собирать результат в обычные WorkflowRevision, StepDefinition и native Call. Новая система runtime-наследования не вводится.
- Сохранить прежний смысл `prifly-project-workflow/1`, немаркированного extend и `prifly-extension/2`. Новые формы включаются явно.

Это изменение продуктового authoring, компиляции и Project CLI. Текущая работа создаёт только планирование; она не меняет код, схемы или настройки smsplace.

### Основной пример и порядок поставки

```text
1. Pri-Fly: imports, наследование общей базы и композиция дополнений
       |
2. Отдельный выпуск workflows: экспорт проверки задачи для UI/UX
       |
3. smsplace: classic → общая база с tests/MR → UI/UX и другие дополнения
       |
   объединение дополнений: sequence / parallel / choice
   определение применимости UI/UX в основном примере обязательно
       +-- требуется --> UI/UX --> результат приёмки
       +-- не требуется --------> причина пропуска
       +-- неизвестно ---------> остановка приёмки
```

Проверку применимости определяет пакет, а не Core и не список расширений файлов внутри движка. Она учитывает реализованную задачу и актуальное состояние кода. Отсутствие данных не означает «UI/UX не нужен».

### Non-goals

- Не изменять canonical classic, UI/UX-пакет или smsplace в этом change.
- Не ускорять `implement`, не менять модели и не выбирать новый основной workflow проекта.
- Не склеивать несвязанные root graphs без общей базы и не выбирать победителя конфликта по порядку родителей.
- Не вводить произвольные JSON patches, runtime plugins или сетевой resolver.
- Не добавлять UI/UX-эвристику, browser adapter или новую repair policy в Core.
- Не обещать автоматическую совместимость ломающего обновления пакета.

## Capabilities

### New Capabilities

Нет. Возможность расширяет существующие source sets; отдельный конкурирующий источник не создаётся.

### Modified Capabilities

- `workflow-and-context`: exports/imports, множественное наследование общей базы, композиция дополнений, упорядоченные слои и typed native bindings.
- `cli-protocol`: читаемый обзор композиции, диагностика конфликтов, prepare/start freshness и безопасный update.
- `published-contracts`: opt-in версии authoring и новых public read forms; сохранение старых схем и Runs.
- `specification-governance`: определения новых authoring-понятий и их граница относительно runtime.

## Impact

Основные области будущей реализации: `cmd/prifly/project_compile.go`, `project_build.go`, `project_extension_call.go`, `project_workflows.go`, Project questionnaire/prepare/start/continue, authoring schemas, capability inventory и `examples/authoring/`.

Нативное исполнение использует существующие Call/Choice/Parallel и последовательные стадии, budgets, claims, resources и trust. Изменение authority state или runtime operator не является целью. Необходимость новых public DTO оформляется отдельными closed versions.

Множественное наследование входит в целевой объём этого change. Реализацию можно выполнять последовательно: imports и один parent, затем общий ancestor и группы. Первый этап не означает готовность всей возможности. Неподдержанные формы до завершения следующих этапов должны явно отказываться.

Текущие нормативные источники: `openspec/specs/{workflow-and-context,cli-protocol,published-contracts}/spec.md` и `openspec/specs/specification-governance/{spec.md,terms.md,agent-brief.md}`. Их ownership не переносится. До применения действуют main specs; delta описывает только явное новое opt-in поведение.

После Core release нужен отдельный запрос в `StenHigh/prifly-aif-workflows`. Пилот в `/srv/projects/smsplace/backend` начинается после выпуска нужного экспорта и проверки его входного контракта.
